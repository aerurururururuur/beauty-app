# 模块架构规约

> 一份写模块时对着抄的规约。每条规则都不是品味问题 —— 它对应一种**不会报错的失败**：类型检查通过、测试全绿、评审看不出，线上悄悄错。

| 项 | 值 |
| --- | --- |
| 适用范围 | `server/src/modules/` 下的业务模块 |
| 技术前提 | TypeScript + Zod · 单进程 Node · JSON 单文件持久化 · 进程内队列 |
| 状态 | 生效 |

本仓**没有数据库** —— 没有 SQL、迁移、事务、审计表、多租户。**每一条规矩都是现在就要守的**；
少数还没做到的标成「待办」，那是欠账不是豁免。

**用法**：新建模块照 §3 起骨架，改代码前查 §15，读不懂某条规矩为什么存在就翻 §14。

## 1. 总纲

整个规约只有三句话。其余十五条都是它们的展开。

> **第一句 · 定义唯一**
> 每个业务概念在全仓只有**一份**定义。第二份定义出现的那天，两份就开始各自演化。

> **第二句 · 跨边界必校验**
> 数据进入领域层之前必须被校验过。类型是编译期承诺，跨边界时它不作数。

> **第三句 · 写入单轨**
> 任何状态变更只有一条路径可走：实体守卫 → 端口 → 仓库实现。没有第二条。

### 为什么按「静默失败」组织，而不是按「最佳实践」

最佳实践清单的问题是：违反它通常不会立刻出事。你会照常提测、照常合并，几周后某个字段开始悄悄不对，而那时没人记得改过什么。

本规约的每一条都写清了它挡住的是什么失败。如果一条规则说不清代价，那它多半只是偏好 —— 偏好不该写成铁律，因为它会稀释真铁律的分量。

### 三条判据

| 判据 | 问法 | 答错时的样子 |
| --- | --- | --- |
| **谁说了算** | 这个形状／规则／文案，全仓有几处定义？ | 两处都「能用」，改一处时另一处不动 |
| **边界在哪** | 这份数据从哪里来？进领域层前过了校验吗？ | 一条不合规数据一路写进 JSON，没人拦 |
| **谁能写** | 改这个状态需要经过哪几步？能不能绕过？ | 有人绕开用例直接改文件，没人知道 |

## 2. 分层与依赖方向

四层，依赖方向单向。这条不是风格，是**可测试性**的前提：领域层不依赖任何东西，才能在零 I/O 的纯内存环境里被穷举测试。

```
┌─────────────────────────────────────────────────────────────────┐
│ 表现层 · presentation                          ← 最外层         │
│ HTTP 控制器 / 路由 / multipart 解析                              │
│ 解析输入、调用应用层、用管道格式化输出                             │
│ 零业务逻辑：不做判断、不拼展示串、不碰存储                          │
└────────────────────────────┬────────────────────────────────────┘
                             │ ↓ 只允许向下调用
┌────────────────────────────▼────────────────────────────────────┐
│ 应用层 · application                                            │
│ 用例编排、原子写边界、权限判定                                     │
│ 不含业务规则 —— 这里的 if 只应表达「先做什么后做什么」              │
└────────────────────────────┬────────────────────────────────────┘
                             │ ↓ 编排领域对象与端口
┌────────────────────────────▼────────────────────────────────────┐
│ 领域层 · domain                                                 │
│ 实体、值对象、规则表、数据形状 Schema、端口 interface              │
│ 零框架、零 I/O、零第三方依赖（校验库是唯一显式豁免）                │
└────────────────────────────▲────────────────────────────────────┘
                             │ ↑ 实现端口，依赖指向抽象
┌────────────────────────────┴────────────────────────────────────┐
│ 基础设施层 · infrastructure                     （虚线，旁挂）    │
│ JSON 仓库、进程内队列、第三方 API 客户端                            │
│ 在出入口强制校验，绝不返回或存储未校验数据                          │
└─────────────────────────────────────────────────────────────────┘
```

> **领域层永远不引用外层任何模块。**
> 若某段规则需要「先查另一份数据才能判」，那它是编排，属于应用层；把查到的结果作为旗标传进实体，让实体做纯判定。

### 依赖方向的可检查形式

不要靠自觉。用一条静态检查把「领域层 import 了外层」变成构建失败：

- 领域层目录下的文件，import 白名单只有：同层文件 + 显式豁免的校验库；
- 应用层不得 import 任何存储实现、HTTP 客户端；
- 表现层不得 import 仓库实现（只经用例）。

这三条都能用一条基于路径的正则检查跑在 CI 里，成本极低，收益是它**永久生效** —— 而架构文档里的「应当」不会。

> **待办**：本仓目前一条架构守卫都没有。这三条是性价比最高的，见 §13.1。

## 3. 标准目录骨架

一个新模块照此起骨架。目录名即层名，让「这段代码该放哪」有一个唯一答案。

```
modules/<module>/
├── compose.ts              组合根：装配依赖、构造用例、导出模块接口（仅组合者导入）
├── index.ts                纯公开面：只有 export，无业务代码
├── domain/
│   ├── schemas/
│   │   ├── entities/       持久化行的形状（一条记录）
│   │   ├── api/            请求 / 响应的形状（DTO）
│   │   ├── contracts/      跨模块 / 跨端契约的形状
│   │   └── index.ts        barrel
│   ├── entities/           实体 + 规则表（状态机 / 归属 / 准入 / 策略）
│   ├── validators/         业务校验实现（豁免 import 校验库）
│   └── ports/              仓储 / 适配器 interface（纯 TS）
├── application/
│   ├── usecases/                      用例类（一个聚合根 / 一条读写链一个）
│   ├── <module>-view.ts               唯一投影管道（§6）
│   └── <shared-piece>.ts              层内私有原子件（读侧投影 / 写侧内核 / 记账）
├── infrastructure/
│   └── <store>-<aggregate>.repository.ts   端口实现（json / in-memory）
└── presentation/
    ├── <module>.controller.ts
    └── routes/<module>.route.ts
```

**只建真有内容的格。** 空目录就是死脚手架 —— 给一个永远不会拨到第二个值的开关，只会得到又一个假开关。
本仓明确**不建**这几格，每条都有替代：

- `schemas/deps/` —— 注入契约的载体是**用例构造器的 `deps` 参数类型**（具名对象、无默认值、用例内零 `new`），不是 schema。
- `ports/public/` + `<mod>.public.service.ts` —— 本仓的跨模块机制方向相反，见 §10。
- `events/` —— 见 §12。
- `errors/` —— `ErrorCode` 是**一张全局协议表**（`shared/domain/errors/app-error.ts`，48 个文件引用）。拆到各模块反而把「错误码即协议」这条破了，所以只在 `shared` 建这一处。
- `utils/` —— 唯一候选 `shared/domain/scene-rules.ts` 是**跨端共享资产**（前端经 vite alias 直接执行同一个文件），搬它要同时改 alias / 脚本深链 / 测试路径断言，只为多一层目录，不划算。

两个约束值得单独记住：

- **目录里有 `index.ts` 就必须走它**（barrel）。深层路径 import 会让「这个文件被谁用」变成不可枚举的问题。
- **新增文件必须补 barrel**。漏了通常不会编译失败 —— 因为没人 import 它就不报错，于是「暂时没消费者」看起来和「根本消费不了」一模一样。

## 4. 数据真理源

### 4.1 每个形状只有一份定义

数据形状的真理源是 `domain/schemas/` 下的 Schema。类型从 Schema **推导**（`z.infer`），schema 与 type 成对导出。

禁止手写 `interface` / `type` 重复描述已有 Schema 的形状。手写的那份没有运行时校验，而且它和 Schema 之间没有任何机制保证同步 —— 它们只会在某次改动后悄悄分叉。

> **判据**
> 同一个字段名出现在两个类型定义里，就要问：这两份**会不会有一天不一样**？会 —— 那就合成一份；不会 —— 那其中一份是多余的。

### 4.2 Schema 只定义形状，不定业务规则

长度上下限、格式、默认值、枚举白名单 —— 这些是**业务规则**，不进 Schema。Schema 只回答「这是什么结构」。

| 放哪 | 内容 | 理由 |
| --- | --- | --- |
| `schemas/` | 字段名、类型、可空性、联合判别键 | 纯形状，可被任何层安全引用 |
| `validators/` | 枚举白名单、格式正则、长度与数值界、归一化、资产域判据 | 规则要能单测、能被注入、能改一处生效 |
| `entities/` | 状态迁移、归属判权、准入条件 | 规则需要「当前状态」这个上下文 |

分界线怎么划，本仓用的口径（写在各 schema 文件的头注释里）：

- schema **留**：字段名、类型（`.int()` 是类型声明，意思是「这不是小数」）、必填与**非空**（`.min(1)` 是「在场」，不是业务下限）、`.strict()`、联合判别键（`z.literal('geometry')`）、`optional()`。
- validator **拿**：枚举白名单、格式正则、业务上下限（`.max(N)` 里 N 是产品决定）、数值界（min / max / positive）。

**规则与它的错误文案必须同处一地。** 这是这一条最实际的收益：搬到 validator 之后，「什么算合法」和「报什么错」在同一行，改一处就生效。反过来，规则留在 schema 里时，第二个入口要么没有它，要么得自己再写一份文案。

> **★ 撤规则之前先问一句：还有谁在靠这个 schema 兜底？**
> 本仓踩过：`agent` 的 `patch_brief` 是全仓唯一不在 `validators/` 里的 schema 解析点，**它后面没有 validator**，靠的就是 schema 里那几个 `z.enum`。把枚举撤出 schema 的那天，模型给的 `occasion: "随便"` 会静默写进会话 brief，一路带到 `POST /api/jobs` 才在另一条路上炸掉。详见 §14-08。

### 4.3 校验器的上限由外部注入，不在文件里写死

「标题 4–30 字」这类可调上限，不要在校验器里写常量。让组合根从配置读出来、构造时注入。这样改配置即改规则，且校验器里永远找不到魔数 —— **魔数是「这条规则还有第二个定义」的最常见形态**。

> **待办**：本仓 §4.2 把上限从 schema 搬进了 validator，**但那只是横向搬家** —— 魔数还在，只换了文件。
> 每个搬进来的常量都在文件头记了「§4.3 欠账」。真兑现要连组合根一起改（配置 → `createXxxModule` → 用例 → 校验器），单列一轮。

### 4.4 派生优于重写，且派生方向要 fail-closed

状态集合这类派生物，从**全集**减去已知可接受的部分，而不是正向列举要拒绝的部分。这样将来新增一个取值时，它默认落进「被拒绝 / 被隐藏」那一侧 —— 安全默认，且立刻表现为测试失败，而不是静默放开。

> **反直觉但重要**
> 有些集合**刻意不派生**。当两个集合不是补集关系时（例如「对作者隐藏的态」与「占用名额的态」有交叠但不等价），推导出来的那天就会有人把它们当成一回事。这类要独立定义，并在注释里写明「为什么不派生」。

### 4.5 规则在领域层，持久层只做拼接

规则本体在领域层；仓库实现只负责**执行**，不发明规则。本仓的落点是 `job-repository.ts` 那条契约 ——
「调用方传入领域迁移函数」：状态能不能这么推进由领域层判，仓库只管把这次读-改-写做成一次原子操作。

同一条判据全仓只有一处定义，所有需要它的地方都引用它。任何「把规则写成查询条件 / 写进仓库实现」的提议
都该先问：**这条规则的第二份定义，是不是正要诞生？**

## 5. 规则的三个落点

一条规则该放哪，取决于它需要什么上下文。三种上下文对应三个落点，不要混。

| 规则的形态 | 落点 | 例子 | 错放的后果 |
| --- | --- | --- | --- |
| 只看输入本身 | `validators/` | 昵称 2–32 字；化妆品名上限；id 格式 | 放进用例 → 第二个入口不会调它 |
| 需要当前状态 / 归属 | `entities/` 的具名守卫 | `assertDeletableBy`、job 的步骤单调推进 | 写在用例里 → 换一条路径就漏判 |
| 需要跨记录事实 | 持久层能表达的约束就交给它；表达不了就**下沉到仓库实现**，并在调用点注释里写明竞态窗口 | 「一人一份」；本仓是「先查后写」 | 把应用层预检当成终局 → TOCTOU 窗口 |

> **本仓现状**：持久层是 JSON 单文件整表读-改-写，**没有唯一约束，也没有 CAS**。
> 「昵称唯一」（`register-user.ts`）这类不变式靠**先查后写**，竞态窗口写在各调用点的注释里，没被假装解决。
> 「下沉到仓库实现」在本仓 = **换一个仓库实现**（`node:sqlite` 零依赖可用），
> 端口契约、用例、校验、路由、测试**一处都不用改** —— 这正是把规则放在那个落点的价值。

### 5.1 纯规则表：把「必须一致」的判据收成一张表

凡是**多个调用点必须逐字一致**的规则，不要在每个调用点各写一个 if，而是收成一张表或一个纯函数，然后让所有调用点引用它。

- **状态机转移表**：动作 → 允许的来源状态集合。守卫引用它，非法迁移当场抛。
  本仓实例：`jobs/domain/entities/job.ts` 的步骤单调推进 —— 纯函数，零 I/O，所以能穷举测试。
- **简报字段的共用规则**：`POST /jobs` 的表单与 agent 的 `patch_brief` 两条入口共用同一份字段规则，收在 `shared/domain/validators/brief-fields.validator.ts`，两边都调它，不各判一次。

另两种形态（**可见性判定**、**派生式隐藏**）本仓暂无对应概念 —— 做内容治理时回来补：前者是「一个具名函数回答『这条对这个人可见吗』，所有读路径引用它」，后者是「子项的可见性派生自父项，而不是在下架时级联改写子项状态」。

### 5.2 用业务话命名守卫，别裸比较字段

调用点要读起来是一句业务话：`if (!ad.isTerminated)` 而不是 `if (post.status !== 'deleted')`。好处不只是可读 —— 日后新增一个「也算终结」的状态时，只有前者不需要改调用点。

同时：**每条规则一个方法**。把「是不是活动帖」和「是不是本人」合成一个 `assertCanRate`，调用点就看不出自己漏了哪条。

## 6. 单一投影管道

内部数据转成对外格式（展示、日志、API 返回、LLM 输入、通知文案）**只能且必须**经过一个命名明确的函数。这就是「输出轨单轨」。

```
   N 条读路径              一个管道                 一个产物            消费者只读
┌──────────────┐    ┌────────────────────┐    ┌──────────────┐    ┌──────────────┐
│ 详情/列表/    │    │  toXxxView()       │    │  带类型标注   │    │ 不重命名字段  │
│ 提交后回包/   │───▶│  穷举每个字段       │───▶│  的 DTO       │───▶│ 不二次格式化  │
│ LLM 上下文    │    │  一处决定：隐私裁剪  │    │  只有管道能   │    │ 不拼展示串    │
│ （取数各不同  │    │  /缺席/引用隔离     │    │  产出该类型   │    │ 需要新信息 →  │
│  但是同一种行）│    │                    │    │              │    │ 管道加字段    │
└──────────────┘    └────────────────────┘    └──────────────┘    └──────────────┘
```

本仓的管道就是各模块的 `application/<module>-view.ts`。

### 哪种判据必须收进管道

判断标准是：**如果两条读路径各写一遍，漂移后会不会有人发现？** 不会的，就必须收。

- **隐私裁剪**：某个字段不该出门。`user-view.ts` 剥掉 `passwordHash` —— 「别绕开它直接回实体」这句话就写在那个文件里，复制一份的后果是密码凭据从某个入口漏出去。
- **缺席的表达**：`weather-view.ts` 只展开有值的字段。缺席不是「零值」，两者的编码方式必须是显式选择的结果，不是顺手的默认。
- **引用隔离**：`cabinet-view.ts` 的特性数组是新建对象，不与实体共享引用。视图一旦被下游改动，不该回头污染领域对象。

### 管道的三条纪律

1. **穷举字段**。新增字段时管道必须编译报错，而不是静默漏掉。别用对象展开把未知字段顺出去 —— 那等于放弃穷举。
2. **缺席要抛，不要兜底成「另一个合法值」**。关联对象取不到就抛错；在管道里补一个 `null` 会让「有归属的内容」静默伪装成「无归属的内容」，而那正是「恒为零的统计量」那种骗过好几轮的形态。
3. **富化结果用具名对象，不用元组**。加第二个富化维度时，元组要逐个改每一条读路径的解构；具名对象只需管道加一行，调用点零改动。

> **形状变更的爆炸半径**
> 改一个字段，只允许改**两个地方**：Schema 真值源 + 这个管道。若还有其他地方报错，说明那里的消费者依赖了数据的具体形状 —— 那是架构违规，要改消费者，不是改规则。

## 7. 跨边界校验

### 7.1 哪些算边界

只要数据来自「你不控制的地方」，就是边界。至少包括：

- HTTP 请求（body / query / path / header）—— 包括 query 里的布尔，`"false"` 字符串转布尔是经典陷阱
- multipart 上传的文件与标量字段（文件名、MIME、字节数都不可信）
- 从 JSON 文件读出的行 —— `JSON.parse` 的结果形状是任意的，`.json` 里的东西可以是手改的
- 进程内队列里的载荷
- 环境变量与配置文件
- 第三方 API 响应（含 LLM 的返回）
- 文件与对象存储的元数据

### 7.2 校验在入口做，且只做一次

`parse()` 放在边界处：值对象构造器（构造即校验）、API 入口、仓库读出口、队列消费入口。已经校验过的数据在管道内部**不要重复 parse** —— 重复校验不会更安全，只会让人以为「还有第二道网」。

**解析点要收进 `validators/`。** 散在别处的 `safeParse` 是 §4.2 的敌人：撤规则时没人知道还有谁在靠它兜底（§14-08 就是这么来的）。本仓现状合规，请保持。

### 7.3 禁止用断言绕过

`as` / `as unknown as` 是「我知道它是什么形状」。在边界处，你不知道。用断言的地方必须能通过全局检索穷举出来，且每一个都有注释说明为什么安全。

> **本仓实例**：`look-spec` 的校验器原先有一句 `parsed.data as LookSpec`。schema 按 §4.2 交出规则后**变宽了**，那句断言就不再安全 —— 现在改成真收窄（类型谓词 + 复合守卫 + 逐字段装配），由编译器证明装配结果正确。

### 7.4 品牌类型用库能力，不手写

需要「只有某个地方能产出这个类型」时，用校验库自带的 brand 能力（它保留形状校验，不需要任何断言）。手写 `& { readonly __brand }` 反而必须靠 `as` 才能赋值 —— 你要的那道防线，自己拆了。

## 8. 写路径单轨

一次状态变更的固定顺序。少一步、错一个顺序，都会留下不可补的窟窿。

1. **表现层只解析入参**
   控制器把原始输入交给用例，不做判断、不组装结果。它不知道业务规则长什么样。

2. **用例跑门控链**
   运行开关 → 登录态 / 归属 → 资源存在性 → 业务准入。**顺序即语义**：谁先撞上决定用户看到哪个错误码，改顺序就是改产品行为。

3. **实体做最终守卫**
   状态机、归属、准入条件在实体上判定，抛领域错误。仓库不重复判规则，只做原子执行。

4. **落库是一次原子写，「期望态检查 + 写入」必须同一临界区**
   `tmp` + `rename` 让**写**是原子的，**读-改-写不是**。所以这件事落在端口契约上而不是用例里 ——
   `job-repository.ts` 那条「调用方传入领域迁移函数」，就是为了让读 / 判 / 写在同一次调用里发生。

5. **业务写与它的记账必须同一次原子提交**
   两件必须一致的事拆成两次写，进程死在中间就留下「状态已变、账没记」。
   本仓的原子单位是**一次文件写**：记账要落就落进同一次写，否则别假装它们是原子的。

6. **先把状态变更落地，再对外宣告**
   宣告（返回 200、推给前端、写进下一个响应）必须在落库**之后**。反过来的话，写失败时你已经把「成了」说出去了，
   而用户看到一个成功的界面配一份没变的文件。

### 三条支撑做法

| 做法 | 为什么 |
| --- | --- |
| **能交给持久层的不变式，就别拿应用层预检当终局** | 预检既有 TOCTOU 窗口，又把同一个判据写成两处。本仓的持久层表达不了约束，那就**换一个实现**（`node:sqlite` 零依赖可用），端口契约与用例不动 —— 而不是加一段「查一下」然后当成解决了。 |
| **实体不做读写往返** | 实体是「只读快照 + 具名守卫」，不是 Active Record。它包装一条记录做前置判定，持久化由仓库完成。 |
| **软删除要区分「谁删的」** | 「作者自己删」与「管理员下架」必须是两个状态。合成一个时：管理员恢复会覆盖作者意图；作者删不掉自己已被下架的内容；作者端无法区分两者。 |

## 9. 归属与越权

本仓**单租户**：没有「多校 / 多组织 / 多工作区」，也没有分片谓词。但「这份数据归谁」这个问题照样存在，而且本仓的答案是被明确接受过代价的。

### 9.1 归属由客户端提交（红线换来的）

`cabinet` 的 `userId` 由客户端显式传，请求体里写谁就是谁 —— 与 §13-5「不签发 token、不建会话」是同一个决定的两面。

代价说清楚：**传对 `userId` 就能读写任何人的衣橱**，没有守卫拦得住。这不是遗漏，是拿红线换来的演示成本。

真作用域的**前提是先有登录态**：有了受信的会话，才能谈「作用域是受信值，不是客户端提交物」；也才谈得上把「这个人属于哪个作用域」与「这个人此刻在管哪个作用域」在类型上分开 —— 后者的失败形态（归属 A、同时是 B 的运营，在 C 端全按 B 算）注释和文档都拦不住。

### 9.2 越权探测：归属不符报 404，不报 403

查不到、或查到了但不属于你 —— **两种情况回同一个错误**（`CABINET_ITEM_NOT_FOUND` / 404）。报 403 等于告诉对方「这条存在，只是不是你的」，逐 id 试一遍就能把别人有哪些条目枚举出来。

无守卫前提下这是最低成本的正确性。测试专门盯着「报错之余**原数据一个字没动**」。

## 10. 跨模块协作

模块之间禁止访问对方的内部实现（仓库、校验器、用例、内部 service），也禁止为对方的数据自建访问器。

**本仓的机制：端口声明在消费方，实现由组装根粘上去。**

| 环节 | 谁做 |
| --- | --- |
| 声明端口 | **消费方**自己在 `domain/ports/` 里声明「我需要什么」（纯 TS，零依赖） |
| 提供实现 | **组装根 `src/index.ts`** 把生产方的 barrel 导出包一层适配成那个端口 |
| 谁 import 谁 | 消费方**不 import 对方的实现** —— 数据类的需求拿的是注入进来的接口；行为类的需求只从对方 barrel 导入（如 agent ← makeup） |

真实例（三处文件头写着同一条理由，照抄即可）：`cabinet/domain/ports/user-directory.ts`（读 user）、
`agent/domain/ports/cosmetic-reader.ts`（读 cabinet）、`agent/domain/ports/product-library.ts`（读 products）。

本仓真正被别家 import 的只有 `shared`、`makeup`、`assets` 三个模块，**全部经 barrel、零深链**。

### 四条纪律

- **跨模块只能从对方模块根导入。**不许深链到对方的端口文件或内部 barrel。
- ★ **镜像端口里的形状要用原始类型重写，一个对方的类型都不借。** 这不是形式主义：`cosmetic-reader.ts` 若借了 cabinet 的 `CosmeticAttribute`，cabinet 改那个类型时 agent 会被动跟着改 —— **这道缝就白留了**。端口只暴露消费方**真正需要**的字段，重复几行结构比借一个类型便宜。
- **依赖要显式声明在用例的注入契约里**，且按约定放在契约最下方（上方是模块内部依赖）。本仓的载体是**用例构造器的 `deps` 参数类型**。
- **跨模块端口刻意不给默认值。**给默认值等于给「忘了传」留后门 —— 那正是需求静默失效的形态。忘了注入就该启动即崩。

> **错误不跨模块抛。** 让端口返回判别式结果（`{ok: false, reason, …}`），消费方据此包装自己的领域错误。否则对方的错误类会泄漏进你的 try/catch 清单。
> （本仓的 `weather-provider` 端口确实带两个契约错误类 —— 但那是**本模块对第三方上游**的端口，翻译点在 `GetWeather` 用例里；真正**跨模块**的那三个端口不抛。）

## 11. 组合根与公开面

两个最外层文件，职责严格分开。混在一起会让「谁能从这里拿到什么」变得不可回答。

| 文件 | 只做 | 绝不做 |
| --- | --- | --- |
| `index.ts` | 纯 barrel：端口契约、schema + type 成对导出、跨模块要用的投影与类型 | 不含任何业务代码；不导出内部实现细节（validator、具体实现类、`createXxxModule`） |
| `compose.ts` | 装配仓库 / 适配器 / 时间源 → 构造用例 → 构造控制器与路由 → 导出模块接口 | 不含业务规则；不导出给非组合者使用的东西 |

> **组合根是唯一可以「知道一切」的地方**
> 只有它同时看见领域、应用、基础设施、表现四层。这个特权一旦扩散到用例里（比如用例自己 `new` 一个仓库），依赖方向就断了，模块也就不再可测。

用例的构造契约里，**不要写默认值**，也不要在用例内部创建依赖。这让「一个用例需要哪些东西」变成一条可读的清单，也让测试只需构造一个假实现。**本仓合规。**

> **待办**：本仓 11 个 barrel 里 10 个还挂着 `createXxxModule` / `Options` / validator / 具体实现类。
> 这是全仓最大的一处偏离，属**机械但面广**的整改（11 个 `index.ts` + 组合者的 import + 少数测试调用点），单列一轮。
> 代价是**「谁能从这里拿到什么」现在不可回答** —— 挂在 `index.ts` 上的东西，看不出哪些是给外部的、哪些只是顺手转出来的。
>
> 例外是**测试接缝**：有些内部件（校验器、行为常量）确实需要被单测直接拿到，那类导出请在 barrel 上**写明理由**，别混在顺手转发里。

## 12. 领域事件

**本仓不使用领域事件。** 需要跨界通知的地方走函数返回值或端口调用 —— agent 的 tool observation 就是前者。

将来真引入事件时，两条约束先立在这里：

- **别为只差一句话的多个事件建多个类。** 一个事件 + 一个 `outcome` 判别字段就够了。六个类意味着六份几乎相同的订阅器拼装，而它们的差别只是字符串。
- **载荷是契约。** 形状进 `schemas/contracts/`，从模块根导出；**文案素材在发布点备齐，订阅器不查库** —— 订阅器一查库，就等于在事件的接收端又开了一条读路径。

## 13. 守卫与门禁

规约若只写在文档里，它就只在被读到的那天生效。以下三类要变成**会自动变红的东西**。

### 13.1 架构守卫（CI 跑的测试）

| 守卫 | 盯什么 | 本仓 |
| --- | --- | --- |
| 分层 import | 领域层零外层依赖；应用层零存储依赖；表现层零仓库依赖 | 待办 · **最该先补** |
| barrel 完整性 | 跨模块只能从模块根导入；内部路径不被外部引用 | 待办 · **最该先补** |
| 契约同步 | 前后端镜像枚举 / 常量一致 | 待办 · **有事故面** |
| 无直接输出 | 禁用裸 console，统一走日志端口 | 待办 |

> **本仓现状：一条都还没建。** 全仓仅有的两条源码扫描断言都只针对 `scene-rules.ts`
> （跨端共享资产：不许有运行时 import、前端的 vite alias 必须指向它），见 `test/scene-rules.test.ts`。
>
> 前两条可查性最高、成本最低 —— 纯路径正则即可，而且它们盯的正是本仓踩过的坑：
> 深链 vs barrel、`test/` 不在 tsconfig 的 `include` 里（漏文件不会报错，静默跳过长得和全绿一模一样）。
>
> ★ **「契约同步」在本仓有真实事故面**：`vue/src/api/agent.js` 里有一份**手工抄的** `MAX_AGENT_TEXT`，
> 改了后端不改前端**不会有任何报错**。同类的还有肤色档位（`assests/face-catalog/` 与 `shared` 之间）。

写守卫时要诚实标注它的**盲区**。一条守卫的名字会让人以为它覆盖了某类问题，而它其实只匹配某种写法（比如别名不同就匹配不到、两片拆到两个文件就漏了）。把盲区写进它的注释里，比多加一条半吊子断言有用。

### 13.2 命令门禁

- **格式检查必须单独跑。**若格式化命令与测试是串联的（测试前先 `--write`），那单独跑测试的你会**永远不知道**有文件没格式化 —— 它被就地修好了。格式检查要么单独列一步，要么换个顺序写它就不存在了。
- **类型检查命令要看配置形状。**本仓有两条：`npm run typecheck`（只覆盖 `src`）与 `npm run typecheck:scripts`。
  ⚠️ **`test/` 不在 `tsconfig.json` 的 `include` 里** —— 测试文件不过类型检查，`npm run typecheck` 绿不代表测试里的类型对。
- **别用管道读门禁结果。**`{ …门禁…; } | tail -20` 的退出码是 `tail` 的，且中间步骤的失败段会被截掉。有人据此把一轮失败报成了全过。重定向到文件再读。
- **哪些命令会改工作树，要标出来。**门禁自己格式化、自己改文件时，跑完先看 `git status` 再提交，否则格式化改动会混进提交里。
- **从零初始化那条路径必须有人真的走一遍。**本仓的对应物是**空 `dataDir`**：目录不存在 / 文件不存在 / JSON 损坏，三种情况各跑一次。别只在自己那份开发数据上验 —— 它早就不代表新用户的第一次启动了。

### 13.3 契约的部署顺序

> **铁律**
> 跨端契约**新增必填字段**时：**后端先上线，前端再上**。反过来的话，前端解析失败的不是那个字段，而是**整个响应** —— 症状与字段毫无关系，会把人带到错的方向去查半天。

本仓前后端同一次演示一起部署，没有「只上一半」的窗口，所以这条退化为**同一次改动里两端同时改**。
但降级不是免费的 —— 风险从「部署顺序」挪到了「**改漏一端**」：手抄的镜像常量
（`vue/src/api/agent.js` 的 `MAX_AGENT_TEXT`、肤色档位）两端之间没有编译期约束，
**漏改不会有任何报错**。跨端改动请显式列出两端各要改哪些文件，别凭记忆。

## 14. 静默失败台账

这一节是全篇最该先读的部分。每一条都写清了：**表面像什么 → 真因是什么 → 立了什么规矩**。

### 01 · 某个字段的语义悄悄变了，而形状测试全绿

- **表面**：两条读路径都能返回合法 DTO，只是其中一条的某个字段算法慢慢不同了。
- **真因**：投影被复制成两份。DTO 形状仍然合法，所以形状测试照不见；漂移是**字段级**的。
- **规矩**：投影收成唯一管道（§6）；判断标准是「复制后漂移了会不会有人发现」。

### 02 · 判据被手抄了第二份，而没有任何断言变红

**本仓暂无对应概念。** 没有内容治理，没有可见性谓词，这一类判据还不存在。

将来做「对谁可见」这类判据时回来补：它的失败形态是判据散在多处、形态还各不相同，
加一个取值时只有一处跟着改 —— 漏改的后果是「本该隐藏的内容从某条读路径漏出去」，而这类缺口类型系统看不见。
规矩是：判据收成一个具名函数，全仓一份，再补一条守卫盯着「有没有人又手写一套」。

### 03 · 加了状态取值之后，某个界面显示成白字透明底

- **表面**：像是设计稿没给这个状态定样式。
- **真因**：展示层的「状态 → 文案 / 颜色」是一张手抄的名单。**解析边界会喊，展示层不喊** —— 后端照常下发新值，前端按缺省渲染，看起来像「设计如此」。
- **规矩**：展示名单写成穷举 Record（缺失即编译失败）+ 一条 CSS 覆盖守卫。

### 04 · 改了一个「不相关」的字段，整个页面白屏

- **表面**：症状指向某个功能模块，看起来像那个模块的 bug。
- **真因**：契约新增了必填字段而前端还没跟上，前端 `parse` 失败的不是那个字段，是**整个响应**。上游为 null → 下游读到空 → 页面显示一句与真因毫不相干的提示。
- **规矩**：见 §13.3 —— 本仓的形态是「两端同一次改，且显式列出两端各要改什么」。

### 05 · 状态变了，但「谁干的」查不到

- **表面**：像是记账那段代码有 bug，或者查询条件写错了。
- **真因**：「业务写」与「记账」是两次独立写入。进程死在中间，就留下「内容已变更、账没记」—— 而记账是 append-only，事后补不回来。
- **规矩**：必须一致的两件事落在**同一次原子提交**里；宣告留在落地**之后**（§8 步骤 5、6）。

### 06 · 一个统计量长期恒为 0，骗过了好几轮验收

- **表面**：像是采集没上报、队列没消费。
- **真因**：「缺席」被兜底成了「零值」，或者某个装配点漏注入导致根本没有产生数据。恒为 0 的数字看起来像「最近确实没有」，不会有人报 bug。
- **规矩**：缺席与 0 是两个概念，分开表达（`null` ≠ `0`）；装配点漏注入要靠「必填不给默认」在启动时拦住。

### 07 · 并发下同一个人提交了两份

- **表面**：像是前端按钮没防抖。
- **真因**：应用层「先查有没有、再插入」的预检存在 TOCTOU 窗口。
- **规矩**：不变式的归宿是**持久层能表达的约束**；本仓的 JSON 单文件表达不了，那就把这条判据**下沉到仓库实现**并写明窗口，
  或者换一个能表达的实现（`node:sqlite`），端口契约与用例不动。**别把预检当成解决了。**

### 08 · 某个校验规则只在一个入口生效

- **表面**：像是那个入口的 bug。
- **真因**：规则写在了用例里而非校验器 / 实体上，第二个入口自然没有它。跨模块重写一份也会造成同样的分叉。
- **规矩**：规则只放三个落点（§5）；上限由组合根注入，文件里找不到魔数。
- ★ **本仓实例（2026-09-29）**：`agent` 的 `patch_brief` 工具是全仓**唯一**不在 `validators/` 里的 schema 解析点，
  而且**后面没有 validator** —— 它连注释都写着「`occasion`/`skinType`/`skinTone` 是枚举，**已由 schema 保证**」。
  它靠的正是那些 `z.enum`：按 §4.2 把枚举撤出 schema，模型给的 `occasion: "随便"`、5000 字的 `sceneText`
  就会**静默写进会话 brief**，一路带到 `POST /api/jobs` 提交时才在**另一条路**上炸掉。
  这是本条的**变体**：规则不是「写在用例里」，而是**「靠另一处的 schema 兜着，而那个 schema 正在被撤掉」**。
  已在同一次改动里堵上 —— 补了 `agent/domain/validators/brief-patch.validator.ts`，让这条路与两个 HTTP 入口
  共用同一份 brief 规则。教训见 §4.2 那个框：撤规则之前先问「还有谁在靠这个 schema 兜底」。

## 16. 反模式速查

| ✗ 反模式 | ✓ 正确形态 |
| --- | --- |
| `interface User { id: string; name: string }` —— 手写第二份形状 | 从 Schema 推导：`type User = z.infer<typeof UserSchema>` |
| Schema 里写 `.min(4).max(30).default('')` | Schema 只写形状；规则进校验器，上限由组合根注入 |
| 在**校验器之外**再 `safeParse` 一次 schema | 解析点收进 `validators/` —— 否则 §4.2 撤规则时没人知道还有谁在靠 schema 兜底（§14-08） |
| `data as User` 绕过校验 | 边界处 `.parse()`；类型收窄用谓词 + 复合守卫，不用断言 |
| 第二条读路径里再写一遍 `status = 'visible'` | 引用唯一的具名判据 |
| 在用例里 `new XxxRepository()` | 构造器接收注入的端口；组合根是唯一知道实现的地方 |
| 用例里写 `if (order.total > 1000) discount = …` | 业务规则下沉到领域层；用例只编排顺序 |
| 跨模块 `import '@other/infrastructure/...'` | 只从对方模块根导入；数据类的需求走**消费方声明的镜像端口**，组装根注入 |
| 镜像端口里借对方的类型 | 用原始类型重写：借一个类型，这道缝就白留了 |
| 展示层拼字符串：`` `${a} · ${b}` `` | 管道产出已拼好的字段，消费者只读 |
| 领域层里 `Date.now()` | 注入时间源 —— 时间是不纯的，也绝不信任客户端时钟。**待办**：本仓 4 个实体的工厂还直接取当前时刻 |
| 给跨模块端口写个默认值「以防忘了传」 | 必填不给默认 —— 忘了传就该启动即崩 |
| 「先查有没有，没有就插入」，然后当成解决了 | 持久层能表达的约束就交给它；表达不了就**下沉到仓库实现**并写明窗口 |
| 先把状态变更说出去，再落库 | 落地之后再宣告 |
| 归属不符时先报 403 再报 404 | 两种情况回同一个 404 —— 403 等于确认「这条存在」 |
| 新增文件后忘了补 barrel | 补上 —— 没人 import 就不报错，「暂无消费者」常其实是「不可消费」 |
| 嵌套三元：`a ? b : c ? d : e` | 展开成 if / else if |
| 注释里写「另有 X 处也这么做」但没核实 | 点名文件前先检索 —— 幽灵引用比没有注释更坏 |
