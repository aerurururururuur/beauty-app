# 模块架构规约

> 一份写模块时对着抄的规约。每条规则都不是品味问题 —— 它对应一种**不会报错的失败**：类型检查通过、测试全绿、评审看不出，线上悄悄错。

| 项 | 值 |
| --- | --- |
| 适用范围 | 单体的业务模块 · 分层架构 · 多租户可选 |
| 技术前提 | 静态类型 + 运行时校验库（本文以 TypeScript + Zod 举例） |
| 状态 | 生效 · 已在生产模块验证 |
| 来源 | 从若干成熟模块的返工与事故中回抽 |

**用法**：新建模块照 §3 起骨架，改代码前查 §15，读不懂某条规矩为什么存在就翻 §14。

## 1. 总纲

整个规约只有三句话。其余十五条都是它们的展开。

> **第一句 · 定义唯一**
> 每个业务概念在全仓只有**一份**定义。第二份定义出现的那天，两份就开始各自演化。

> **第二句 · 跨边界必校验**
> 数据进入领域层之前必须被校验过。类型是编译期承诺，跨边界时它不作数。

> **第三句 · 写入单轨**
> 任何状态变更只有一条路径可走：实体守卫 → 仓储接口 → 持久化。没有第二条。

### 为什么按「静默失败」组织，而不是按「最佳实践」

最佳实践清单的问题是：违反它通常不会立刻出事。你会照常提测、照常合并，几周后某个字段开始悄悄不对，而那时没人记得改过什么。

本规约的每一条都写清了它挡住的是什么失败。如果一条规则说不清代价，那它多半只是偏好 —— 偏好不该写成铁律，因为它会稀释真铁律的分量。

### 三条判据

| 判据 | 问法 | 答错时的样子 |
| --- | --- | --- |
| **谁说了算** | 这个形状／规则／文案，全仓有几处定义？ | 两处都「能用」，改一处时另一处不动 |
| **边界在哪** | 这份数据从哪里来？进领域层前过了校验吗？ | 线上一条不合规数据一路走到 DB，没人拦 |
| **谁能写** | 改这个状态需要经过哪几步？能不能绕过？ | 有人直连 DB 改了一行，审计表里没有记录 |

## 2. 分层与依赖方向

四层，依赖方向单向。这条不是风格，是**可测试性**的前提：领域层不依赖任何东西，才能在零 I/O 的纯内存环境里被穷举测试。

```
┌─────────────────────────────────────────────────────────────────┐
│ 表现层 · presentation                          ← 最外层         │
│ HTTP 控制器 / CLI / WebSocket                                   │
│ 解析输入、调用应用层、用管道格式化输出                            │
│ 零业务逻辑：不做判断、不拼展示串、不碰 DB                          │
└────────────────────────────┬────────────────────────────────────┘
                             │ ↓ 只允许向下调用
┌────────────────────────────▼────────────────────────────────────┐
│ 应用层 · application                                            │
│ 用例编排、事务边界、权限判定、事件发布                             │
│ 不含业务规则 —— 这里的 if 只应表达「先做什么后做什么」              │
└────────────────────────────┬────────────────────────────────────┘
                             │ ↓ 编排领域对象与端口
┌────────────────────────────▼────────────────────────────────────┐
│ 领域层 · domain                                                 │
│ 实体、值对象、规则表、数据形状 Schema、端口 interface              │
│ 零框架、零 I/O、零第三方依赖（校验库是唯一显式豁免，见 §4.4）        │
└────────────────────────────▲────────────────────────────────────┘
                             │ ↑ 实现端口，依赖指向抽象
┌────────────────────────────┴────────────────────────────────────┐
│ 基础设施层 · infrastructure                     （虚线，旁挂）    │
│ 数据库实现、缓存、第三方 API 客户端                                │
│ 在出入口强制校验，绝不返回或存储未校验数据                          │
└─────────────────────────────────────────────────────────────────┘
```

> **领域层永远不引用外层任何模块。**
> 若某段规则需要「查一下另一张表才能判」，那它是编排，属于应用层；把 I/O 结果作为旗标传进实体，让实体做纯判定。

### 依赖方向的可检查形式

不要靠自觉。用一条静态检查把「领域层 import 了外层」变成构建失败：

- 领域层目录下的文件，import 白名单只有：同层文件 + 显式豁免的校验库；
- 应用层不得 import 任何数据库驱动、HTTP 客户端、ORM；
- 表现层不得 import 仓储实现（只经用例）。

这三条都能用一条基于路径的正则检查跑在 CI 里，成本极低，收益是它**永久生效** —— 而架构文档里的「应当」不会。

## 3. 标准目录骨架

一个新模块照此起骨架。目录名即层名，让「这段代码该放哪」有一个唯一答案。

```
modules/<module>/
├── compose.ts              组合根：装配依赖、构造用例、导出模块接口（仅组合者导入）
├── index.ts                纯公开面：只有 export，无业务代码
├── domain/
│   ├── schemas/
│   │   ├── entities/       持久化行的形状（table row）
│   │   ├── api/            请求 / 响应的形状（DTO）
│   │   ├── contracts/      事件载荷等对外契约
│   │   ├── deps/           用例的注入契约（端口以 custom<> 声明）
│   │   └── index.ts        barrel
│   ├── entities/           实体 + 规则表（状态机 / 可见性 / 阶段 / 策略）
│   ├── validators/         业务校验实现（豁免 import 校验库）
│   ├── ports/              仓储 / 适配器 interface（纯 TS）
│   │   └── public/         跨模块端口契约
│   ├── events/             领域事件类
│   ├── errors/             领域错误类（错误码即协议）
│   └── utils/              纯函数（无状态、无 I/O）
├── application/
│   ├── <module>.usecase.ts            用例类（一个聚合根 / 一条读写链一个）
│   ├── <module>-view.ts               唯一投影管道（§6）
│   ├── <module>-*.public.service.ts   跨模块端口的实现
│   └── <shared-piece>.ts              层内私有原子件（读侧投影 / 写侧内核 / 审计）
├── infrastructure/
│   ├── pg-<aggregate>.repository.ts   端口实现
│   └── <rule>-sql.ts                  领域规则的 SQL 渲染（§4.5）
└── presentation/
    ├── <module>.controller.ts
    └── routes/<module>.route.ts
```

两个约束值得单独记住：

- **目录里有 `index.ts` 就必须走它**（barrel）。深层路径 import 会让「这个文件被谁用」变成不可枚举的问题。
- **新增文件必须补 barrel**。漏了通常不会编译失败 —— 因为没人 import 它就不报错，于是「暂时没消费者」看起来和「根本消费不了」一模一样。

## 4. 数据真理源

### 4.1 每个形状只有一份定义

数据形状的真理源是 `domain/schemas/` 下的 Schema。类型从 Schema **推导**（`z.infer`），schema 与 type 成对导出。

禁止手写 `interface` / `type` 重复描述已有 Schema 的形状。手写的那份没有运行时校验，而且它和 Schema 之间没有任何机制保证同步 —— 它们只会在某次改动后悄悄分叉。

> **判据**
> 同一个字段名出现在两个类型定义里，就要问：这两份**会不会有一天不一样**？会 —— 那就合成一份；不会 —— 那其中一份是多余的。

### 4.2 Schema 只定义形状，不定业务规则

长度上下限、格式、默认值、枚举白名单 —— 这些是**业务规则**，不进 Schema。Schema 只回答「这是什么结构」。

| 放哪 | 内容 | 理由 |
| --- | --- | --- |
| `schemas/` | 字段名、类型、可空性、联合分支 | 纯形状，可被任何层安全引用 |
| `validators/` | 长度、格式、上限、归一化、资产域判据 | 规则要能单测、能被注入、能改一处生效 |
| `entities/` | 状态迁移、归属判权、准入条件 | 规则需要「当前状态」这个上下文 |

### 4.3 校验器的上限由外部注入，不在文件里写死

「标题 4–30 字」这类可调上限，不要在校验器里写常量。让组合根从配置读出来、构造时注入。这样改配置即改规则，且校验器里永远找不到魔数 —— **魔数是「这条规则还有第二个定义」的最常见形态**。

### 4.4 派生优于重写，且派生方向要 fail-closed

状态集合这类派生物，从**全集**减去已知可接受的部分，而不是正向列举要拒绝的部分。这样将来新增一个取值时，它默认落进「被拒绝 / 被隐藏」那一侧 —— 安全默认，且立刻表现为测试失败，而不是静默放开。

> **反直觉但重要**
> 有些集合**刻意不派生**。当两个集合不是补集关系时（例如「对作者隐藏的态」与「占用名额的态」有交叠但不等价），推导出来的那天就会有人把它们当成一回事。这类要独立定义，并在注释里写明「为什么不派生」。

### 4.5 规则在领域层，SQL 只做渲染

当一条规则既要被 TS 判定、又要出现在 SQL 谓词里时（数据量大、必须在库里过滤），正确做法是：**规则本体在领域层，SQL 侧只写一个渲染函数**，把领域枚举摊平成 SQL 片段。

- 渲染件放在基础设施层，且**不发明规则** —— 它没有判断，只有拼接；
- 同一条谓词全仓只有一处定义，所有需要它的查询都引用它；
- SQL 里必须出现字面量的地方（如部分唯一索引的谓词），用一条**契约测试**断言「迁移里的字面量 == 领域枚举的取值」，因为不同步的后果是静默的。

## 5. 规则的三个落点

一条规则该放哪，取决于它需要什么上下文。三种上下文对应三个落点，不要混。

| 规则的形态 | 落点 | 例子 | 错放的后果 |
| --- | --- | --- | --- |
| 只看输入本身 | `validators/` | 标题 4–30 字；图片 URL 必须属于自家域 | 放进用例 → 第二个入口不会调它 |
| 需要当前状态 / 归属 | `entities/` 的具名守卫 | `assertDeletableBy`、`assertModeratableTo` | 写在用例里 → 换一条路径就漏判 |
| 需要跨行 / 跨表事实 | 数据库约束优先，否则应用层编排 | 「一人一稿」用部分唯一索引 | 应用层预检 → TOCTOU 窗口 |

### 5.1 纯规则表：把「必须一致」的判据收成一张表

凡是**多个调用点必须逐字一致**的规则，不要在每个调用点各写一个 if，而是收成一张表或一个纯函数，然后让所有调用点引用它。

- **状态机转移表**：动作 → 允许的来源状态集合。实体守卫引用它，仓储 SQL 的 `WHERE status = 期望值` 是它的并发围栏（方向一致，但 SQL 只负责防竞态）。
- **可见性判定**：一个具名函数回答「这条内容对这个人可见吗」，SQL 侧渲染同一个判据。原先散在六处 SQL 谓词里的同一语义，形态还各不相同 —— 漏改一处的后果是「本该隐藏的内容从某条读路径漏出去」，而这类缺口类型系统看不见。
- **派生式隐藏**：子项的可见性**派生自父项**，而不是在下架时级联改写子项状态。级联改写会把「子项为何消失」这个事实只留在父行，且恢复父项后子项再也回不来。

### 5.2 用业务话命名守卫，别裸比较字段

调用点要读起来是一句业务话：`if (!ad.isTerminated)` 而不是 `if (post.status !== 'deleted')`。好处不只是可读 —— 日后新增一个「也算终结」的状态时，只有前者不需要改调用点。

同时：**每条规则一个方法**。把「是不是活动帖」和「是不是本人」合成一个 `assertCanRate`，调用点就看不出自己漏了哪条。

## 6. 单一投影管道

内部数据转成对外格式（展示、日志、API 返回、LLM 输入、通知文案）**只能且必须**经过一个命名明确的函数。这就是「输出轨单轨」。

```
   N 条读路径              一个管道                 一个产物            消费者只读
┌──────────────┐    ┌────────────────────┐    ┌──────────────┐    ┌──────────────┐
│ feed/详情/    │    │  toXxxView()       │    │  带品牌类型   │    │ 不重命名字段  │
│ 作者页/搜索/  │───▶│  穷举每个字段       │───▶│  的 DTO       │───▶│ 不二次格式化  │
│ 活动内列表    │    │  一处决定：隐私裁剪  │    │  只有管道能   │    │ 不拼展示串    │
│ （SQL 各不相同│    │  /自见态/富化解析   │    │  产出该类型   │    │ 需要新信息 →  │
│  但是同一种行）│    │                    │    │              │    │ 管道加字段    │
└──────────────┘    └────────────────────┘    └──────────────┘    └──────────────┘
```

### 哪种判据必须收进管道

判断标准是：**如果两条读路径各写一遍，漂移后会不会有人发现？** 不会的，就必须收。

- **隐私裁剪**：某个字段只对特定 viewer 可见（例如浏览量仅作者可见），其余人收到 `null`。复制一份的后果是某个入口开始泄漏。
- **自见态打标**：内容对作者本人携带状态（他自己的待审内容也在自己视野里），对他人不携带。漏了会把「待审」伪装成「已公开」。
- **批量富化**：关联对象（作者资料、归属对象）怎么查、查哪些 id、去重、空集短路、几路并行 —— 全部收在一处。

### 管道的三条纪律

1. **穷举字段**。新增字段时管道必须编译报错，而不是静默漏掉。别用对象展开把未知字段顺出去 —— 那等于放弃穷举。
2. **缺席要抛，不要兜底成「另一个合法值」**。关联对象取不到就抛错；在管道里补一个 `null` 会让「有归属的内容」静默伪装成「无归属的内容」，而那正是「恒为零的统计量」那种骗过好几轮的形态。
3. **富化结果用具名对象，不用元组**。加第二个富化维度时，元组要逐个改每一条读路径的解构；具名对象只需管道加一行，调用点零改动。

> **形状变更的爆炸半径**
> 改一个字段，只允许改**两个地方**：Schema 真值源 + 这个管道。若还有其他地方报错，说明那里的消费者依赖了数据的具体形状 —— 那是架构违规，要改消费者，不是改规则。

## 7. 跨边界校验

### 7.1 哪些算边界

只要数据来自「你不控制的地方」，就是边界。至少包括：

- HTTP 请求（body / query / path / header）—— 包括 query 里的布尔，`"false"` 字符串转布尔是经典陷阱
- 数据库读出的行（驱动可能把 bigint 返回成字符串、把 jsonb 返回成任意结构）
- 消息队列 / 事件总线上的载荷
- 环境变量与配置文件
- 第三方 API 响应
- 文件与对象存储的元数据

### 7.2 校验在入口做，且只做一次

`parse()` 放在边界处：值对象构造器（构造即校验）、API 入口、仓储读出口、事件订阅器入口。已经校验过的数据在管道内部**不要重复 parse** —— 重复校验不会更安全，只会让人以为「还有第二道网」。

### 7.3 禁止用断言绕过

`as` / `as unknown as` 是「我知道它是什么形状」。在边界处，你不知道。用断言的地方必须能通过全局检索穷举出来，且每一个都有注释说明为什么安全。

### 7.4 品牌类型用库能力，不手写

需要「只有某个地方能产出这个类型」时，用校验库自带的 brand 能力（它保留形状校验，不需要任何断言）。手写 `& { readonly __brand }` 反而必须靠 `as` 才能赋值 —— 你要的那道防线，自己拆了。

## 8. 写路径单轨

一次状态变更的固定顺序。少一步、错一个顺序，都会留下不可补的窟窿。

1. **表现层只解析入参**
   控制器把原始输入交给用例，不做判断、不组装结果。它不知道业务规则长什么样。

2. **用例跑门控链**
   运行开关 → 认证 / 授权 → 资源可见性 → 业务准入。**顺序即语义**：谁先撞上决定用户看到哪个错误码，改顺序就是改产品行为。

3. **实体做最终守卫**
   状态机、归属、准入条件在实体上判定，抛领域错误。仓储不重复判规则，只做原子执行。

4. **仓储用 CAS 落库**
   `UPDATE … WHERE id = ? AND status = 期望态 RETURNING`。零行 = 冲突 / 不存在，当场抛。不捕唯一约束异常，把冲突表达在 SQL 里。

5. **业务写 + 审计行同事务**
   拆成两条独立语句时，进程死在中间就留下「内容已变更、审计表无行」——「谁干的」永久丢失，而审计表是 append-only，事后补不回来。

6. **事件在事务之外发布**
   事务一旦回滚，那条事件就是「为一件没发生的事发的通知」。顺序：先提交，再广播。

### 三条支撑做法

| 做法 | 为什么 |
| --- | --- |
| **能交给数据库的不变式，就交给数据库** | 「一人一份」这类约束用部分唯一索引表达，并让状态变化**自动**把行移出索引 —— 名额释放不需要任何代码。应用层预检既有 TOCTOU 窗口，又会把同一个谓词写成两处。 |
| **实体不做读写往返** | 实体是「只读快照 + 具名守卫」，不是 Active Record。它包装一行做前置判定，持久化由仓储的原子语句完成。 |
| **软删除要区分「谁删的」** | 「作者自己删」与「管理员下架」必须是两个状态。合成一个时：管理员恢复会覆盖作者意图；作者删不掉自己已被下架的内容；作者端无法区分两者。 |

---

## 9. 作用域分片

多租户（多校 / 多组织 / 多工作区）场景下，作用域是**架构级不变式**，不是查询参数。

### 9.1 作用域是受信值，不是客户端提交物

作用域由边界解析后产出，客户端不能自由提交。取不到上下文即拒绝 —— **绝不退化为「返回全部」**。

### 9.2 两种作用域判据要在类型上分开

这是最容易出事、也最难自查的一处：同一个「哪所学校 / 哪个组织」，背后有两种互不通用的判据。

| 判据 | 含义 | 产出者 | 用在哪 |
| --- | --- | --- | --- |
| **参与侧** | 这个人**属于**哪个作用域 | 归属解析 | C 端读写自己的内容 |
| **运营侧** | 这个人此刻**在管**哪个作用域 | 授权集合解析 | 治理端 / 后台 |

两者被合成一个判据时的症状：「归属 A、同时是 B 的运营」的人在 C 端全部按 B 算，而超级管理员被解析成「目录里的第一个」。**注释和文档都拦不住这个** —— 要靠品牌类型把它们在编译期分开，并且**只在解析器里产出**这两个值。

### 9.3 分片在持久层强制，不在应用层自觉

用会话级变量 + 谓词常量，让每条读写都带上分片条件。事务开始时就设好这个变量：这样事务内任何忘记套谓词的查询会**当场报错**（fail-closed），而不是静默跨作用域。

两类守卫都要有：**正向**断言「文件里出现了谓词」，**反向**断言「某几条刻意跨作用域的读路径里不许出现它」。只有正向时，给跨作用域路径补一句谓词不会让任何测试变红。

## 10. 跨模块协作

模块之间禁止访问对方的内部实现（仓储、校验器、用例、内部 service），也禁止为对方的数据自建访问器。每个模块对外只发布**一个公共端口契约**。

| 文件 | 位置 | 内容 |
| --- | --- | --- |
| `xxx-module.public.port.ts` | `domain/ports/` | 接口定义（纯 TS，零依赖） |
| `xxx-module.public.service.ts` | `application/` | 实现类 |
| `index.ts` | 模块最外层 | **纯 barrel**，只发布端口 / 服务 / schema+type / 事件 |
| `compose.ts` | 模块最外层 | 组合根，仅组合者从 `compose.js` 导入 |

### 四条纪律

- **跨模块只能从对方模块根导入。**不许深链到对方的端口文件或内部 barrel。
- **依赖要显式声明在用例的注入契约里**，且按约定放在契约最下方（上方是模块内部依赖）。形状靠 Schema，端口靠 `custom<>` 标记。
- **跨模块端口刻意不给默认值。**给默认值等于给「忘了传」留后门 —— 那正是需求静默失效的形态。忘了注入就该启动即崩。
- **错误不跨模块抛。**让端口返回判别式结果（`{ok: false, reason, currentStatus}`），消费方据此包装自己的领域错误。否则对方的错误类会泄漏进你的 try/catch 清单。

---

## 11. 组合根与公开面

两个最外层文件，职责严格分开。混在一起会让「谁能从这里拿到什么」变得不可回答。

| 文件 | 只做 | 绝不做 |
| --- | --- | --- |
| `index.ts` | 纯 barrel：端口契约、公共 service、schema + type 成对导出、领域事件 | 不含任何业务代码；不导出内部实现细节（deps schema、validator、`createXxxModule`） |
| `compose.ts` | 装配仓储 / 适配器 / 校验器 / 时间源 → 构造用例 → 构造控制器与路由 → 导出模块接口 | 不含业务规则；不导出给非组合者使用的东西 |

> **组合根是唯一可以「知道一切」的地方**
> 只有它同时看见领域、应用、基础设施、表现四层。这个特权一旦扩散到用例里（比如用例自己 `new` 一个仓储），依赖方向就断了，模块也就不再可测。

用例的构造契约里，**不要写默认值**，也不要在用例内部创建依赖。这让「一个用例需要哪些东西」变成一条可读的清单，也让测试只需构造一个假实现。

## 12. 领域事件

事件 = 「聚合已变化、他方需要被告知」的不可变宣告。它**不含行为**，也不被持久化。

### 什么时候不要新建事件类

当多个事件只差文案里的一句话时，用一个事件 + 一个 `outcome` 判别字段，而不是建六个类。六个类意味着六份几乎相同的订阅器拼装 —— 而它们的差别只是字符串。

### 事件载荷是契约

载荷形状进 `schemas/contracts/`，消费方要用到的字段类型从模块根导出。文案素材在发布点备齐，订阅器不查库 —— 订阅器一查库，就等于在事件的接收端又开了一条读路径。

## 13. 守卫与门禁

规约若只写在文档里，它就只在被读到的那天生效。以下三类要变成**会自动变红的东西**。

### 13.1 架构守卫（CI 跑的测试）

| 守卫 | 盯什么 |
| --- | --- |
| 分层 import | 领域层零外层依赖；应用层零驱动依赖；表现层零仓储依赖 |
| barrel 完整性 | 跨模块只能从模块根导入；内部路径不被外部引用 |
| 谓词 SSOT | 组合形状（可见性 / 分片）全仓只许出现在渲染文件里 |
| 契约同步 | 迁移里的字面量 == 领域枚举取值；前后端镜像枚举一致 |
| 写入路径 | 不存在绕过实体方法 / 仓储接口的直改 |
| 无直接输出 | 禁用裸 console，统一走日志端口 |

写守卫时要诚实标注它的**盲区**。一条守卫的名字会让人以为它覆盖了某类问题，而它其实只匹配某种写法（比如别名不同就匹配不到、两片拆到两个文件就漏了）。把盲区写进它的注释里，比多加一条半吊子断言有用。

### 13.2 命令门禁

- **格式检查必须单独跑。**若格式化命令与测试是串联的（测试前先 `--write`），那单独跑测试的你会**永远不知道**有文件没格式化 —— 它被就地修好了。格式检查要么单独列一步，要么换个顺序写它就不存在了。
- **类型检查命令要看配置形状。**solution-style 的 tsconfig（`files: []` + `references`）下，裸跑类型检查的输入文件集为空 —— 它查了个空、永远成功。同一句命令在不同子项目里可能一个真跑、一个空转，**抄命令抄不出门禁**。
- **别用管道读门禁结果。**`{ …门禁…; } | tail -20` 的退出码是 `tail` 的，且中间步骤的失败段会被截掉。有人据此把一轮失败报成了全过。
- **哪些命令会改工作树，要标出来。**门禁自己格式化、自己改文件时，跑完先看 `git status` 再提交，否则格式化改动会混进提交里。
- **空库跑一遍迁移链。**本机库是长期增量演进的 —— 一条顺序有缺陷的迁移在开发库上早就应用过，永远不会重蹈；只有全新库会按时间戳真正跑到它。这条只能放 CI。

### 13.3 契约的部署顺序

> **铁律**
> 跨端契约**新增必填字段**时：**后端先上线，前端再上**。反过来的话，前端解析失败的不是那个字段，而是**整个响应** —— 症状与字段毫无关系，会把人带到错的方向去查半天。

## 14. 静默失败台账

这一节是全篇最该先读的部分。每一条都是从真实返工里回抽的：**表面像什么 → 真因是什么 → 立了什么规矩**。

### 01 · 某个字段的语义悄悄变了，而形状测试全绿

- **表面**：两条读路径都能返回合法 DTO，只是其中一条的某个字段算法慢慢不同了。
- **真因**：投影被复制成两份。DTO 形状仍然合法，所以形状测试照不见；漂移是**字段级**的。
- **规矩**：投影收成唯一管道；判断标准是「复制后漂移了会不会有人发现」。

### 02 · 搜索能搜到已下架的内容

- **表面**：像是搜索索引或缓存的问题。
- **真因**：搜索的可见性谓词被手抄了第二份，且没有断言会因此变红。枚举加值在 `z.infer` 下是**静默拓宽**，没有任何穷举点会报错。
- **规矩**：可见性谓词全仓一份 + 一条架构守卫盯着「有没有人再手写一套」。

### 03 · 加了状态取值之后，某个界面显示成白字透明底

- **表面**：像是设计稿没给这个状态定样式。
- **真因**：展示层的「状态 → 文案 / 颜色」是一张手抄的名单。**解析边界会喊，展示层不喊** —— 后端照常下发新值，前端按缺省渲染，看起来像「设计如此」。
- **规矩**：展示名单写成穷举 Record（缺失即编译失败）+ 一条 CSS 覆盖守卫。

### 04 · 改了一个「不相关」的字段，整个页面白屏

- **表面**：症状指向某个功能模块，看起来像那个模块的 bug。
- **真因**：契约新增了必填字段而后端还没部署，前端 `parse` 失败的不是那个字段，是**整个响应**。上游为 null → 下游读到空 → 页面显示一句与真因毫不相干的提示。
- **规矩**：契约加必填字段：后端先发、前端后发。

### 05 · 审计表里查不到某次操作是谁做的

- **表面**：像是审计表写了 bug，或者查询条件写错了。
- **真因**：「业务写」与「审计落行」是两条独立语句。进程死在中间，就留下「内容已变更、审计表无行」—— 而审计表 append-only，事后补不回来。
- **规矩**：业务写与审计行同事务；**事件发布留在事务之外**，否则回滚后会为一件没发生的事发通知。

### 06 · 一个统计量长期恒为 0，骗过了好几轮验收

- **表面**：像是采集没上报、队列没消费。
- **真因**：「缺席」被兜底成了「零值」，或者某个装配点漏注入导致根本没有产生行。恒为 0 的数字看起来像「最近确实没有」，不会有人报 bug。
- **规矩**：缺席与 0 是两个概念，分开表达（`null` ≠ `0`）；装配点漏注入要靠「必填不给默认」在启动时拦住。

### 07 · 并发下同一个人提交了两份

- **表面**：像是前端按钮没防抖。
- **真因**：应用层「先查有没有、再插入」的预检存在 TOCTOU 窗口。
- **规矩**：不变式交给数据库：部分唯一索引 + `ON CONFLICT DO NOTHING` 空返回即「已占用」。名额释放靠状态变化自动移出索引，不需要释放代码。


### 08 · 某个校验规则只在一个入口生效

- **表面**：像是那个入口的 bug。
- **真因**：规则写在了用例里而非校验器 / 实体上，第二个入口自然没有它。跨模块重写一份也会造成同样的分叉。
- **规矩**：规则只放三个落点（§5）；上限由组合根注入，文件里找不到魔数。

## 15. 上手检查清单

按你正在做的动作查。每条都能在几分钟内确认。

### 新建一个模块

- [ ] 目录骨架照 §3 起，五个层目录 + `compose.ts` + `index.ts` 一个不缺
- [ ] `index.ts` 是纯 barrel：只有 export，无业务代码
- [ ] 组合根里**唯一**装配所有依赖；用例构造器里没有任何 `new`
- [ ] 跨模块依赖写进 deps 契约最下方，且**不给默认值**
- [ ] 领域层里 grep 一遍：没有数据库驱动、没有 HTTP 客户端、没有校验库以外的第三方

### 给已有数据结构加一个字段

- [ ] 只改两处：Schema 真值源 + 单一投影管道。其他地方报错说明消费者违规
- [ ] 管道里**穷举**了新字段（不是靠对象展开顺出去）
- [ ] 跨端契约：确认**后端先上线**，或前端这一版能容忍旧后端（并在注释写明撤除时机）
- [ ] 若字段是图片 / URL：判据走既有的资产域校验，不要自己写 hostname 或前缀比较
- [ ] 同步更新表结构文档

### 新增一个状态取值 / 枚举值

- [ ] 列出它的**所有消费面**：状态机转移表、可见性派生集合、展示名单（文案 + 颜色）、SQL 里的字面量
- [ ] 展示名单若是手抄的，补成穷举 Record —— 缺失应该是编译失败
- [ ] 若有 SQL 侧字面量：补一条契约测试断言「迁移 == 领域枚举」
- [ ] 问一遍：它默认落进「安全那侧」吗？（fail-closed）
- [ ] 治理端的枚举镜像（如果有前后端两份）要一起改

### 新增一条读路径

- [ ] 可见性 / 分片谓词**引用**既有渲染件，没有手写第二套
- [ ] 输出走既有投影管道，没有为这条路径另写格式化
- [ ] 批量富化走既有装配点（查哪些 id、去重、空集短路、几路并行）
- [ ] 排序键是否可变？可变的话不能做游标（时间戳可以，算分不行）

### 新增一条写路径

- [ ] 门控链的**顺序**想清楚了 —— 顺序即用户看到的错误码
- [ ] 状态 / 归属 / 准入判定在实体守卫里，不在用例的 if 里
- [ ] 落库是 CAS（`WHERE 期望态`），零行当场抛
- [ ] 若伴随审计 / 台账写入 → 同事务；若伴随事件 → 事务**外**发布
- [ ] 并发不变式能用数据库约束表达吗？能就别用应用层预检

### 提交之前

- [ ] 格式检查**单独**跑过 `--check`（没有 test 帮你顺手格式化）
- [ ] 类型检查命令在这个子项目里是真跑的（看 tsconfig 形状，不是抄命令）
- [ ] 门禁结果重定向到文件再读，不是管道 `| tail`
- [ ] 跑完 `git status`：门禁自己格式化过的工作树改动不要混进提交
- [ ] 改动触碰到架构守卫吗？（跨层 import / 新增谓词 / 新增枚举）先本地跑那几条

## 16. 反模式速查

| ✗ 反模式 | ✓ 正确形态 |
| --- | --- |
| `interface User { id: string; name: string }` —— 手写第二份形状 | 从 Schema 推导：`type User = z.infer<typeof UserSchema>` |
| Schema 里写 `.min(4).max(30).default('')` | Schema 只写形状；规则进校验器，上限由组合根注入 |
| `data as User` 绕过校验 | 边界处 `.parse()`；品牌类型用库能力，不用手写断言 |
| 第二条读路径里再写一遍 `status = 'visible'` | 引用唯一的谓词渲染件 |
| 在用例里 `new PgXxxRepository()` | 构造器接收注入的端口；组合根是唯一知道实现的地方 |
| 用例里写 `if (order.total > 1000) discount = …` | 业务规则下沉到领域层；用例只编排顺序 |
| 跨模块 `import '@other/infrastructure/...'` | 只从对方模块根导入公共端口 |
| 展示层拼字符串：`` `${a} · ${b}` `` | 管道产出已拼好的字段，消费者只读 |
| 领域层里 `Date.now()` | 注入时间源 —— 时间是不纯的，也绝不信任客户端时钟 |
| 给跨模块端口写个默认值「以防忘了传」 | 必填不给默认 —— 忘了传就该启动即崩 |
| 「先查有没有，没有就插入」 | 唯一约束 + `ON CONFLICT`；不变式交给数据库 |
| 事件在事务里发布 | 提交之后再广播 |
| 新增文件后忘了补 barrel | 补上 —— 没人 import 就不报错，「暂无消费者」常其实是「不可消费」 |
| 嵌套三元：`a ? b : c ? d : e` | 展开成 if / else if |
| 注释里写「另有 X 处也这么做」但没核实 | 点名文件前先检索 —— 幽灵引用比没有注释更坏 |

---
