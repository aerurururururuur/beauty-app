## 1. 目标与非目标

### 1.1 目标

| # | 目标 | 归哪一层 |
| --- | --- | --- |
| G1 | 用户照片 + 简报 → **真实的、像本人**的上妆成片（不是 CSS 叠加示意） | 层 A |
| G2 | 用户用自然语言多轮描述需求，系统逐步收敛到一套妆面，而不是一次填完长表单 | 层 B |
| G3 | 对话过程不烧钱、不平庸地等待——**大部分轮次免费且瞬时** | 层 B |
| G4 | 现有一次性表单路径**不退化**，且继续作为 demo 兜底 | 两层 |

### 1.2 非目标（本轮明确不做）

- **不做服务端登录态。** agent 会话的归属沿用 cabinet 的先例（客户端显式传 `userId`），
  理由与代价见红线 §13-5，本文不改这条。
- **不做视觉读图**（LLM 看用户照片判断肤色/脸型）。这是 `roadmap.md` §4 那个一直没建的接缝，
  本次**只预留位置不实现**——见 §7.2 的 `describe_face` 条目。
- **不做多会话管理 / 历史列表 / 跨设备同步。** 单会话跑通即可。
- **不引外部 agent 框架**（LangChain / Vercel AI SDK 等）。见 §7.3 末。

## 2. 为什么必须分成两层

用户的话是"接入 ai 生图引擎，**同时**做成一个 agent"。这两件事的依赖关系是单向的：

```
层 B（agent）  ──依赖──▶  层 A（引擎）
   没有 A，B 只是一个会说漂亮话、但拿不出图的木偶
```

| | 层 A：引擎落地 | 层 B：agent 层 |
| --- | --- | --- |
| 交付物 | `Engine` 端口的一个真实实现 | 新的 `agent` 模块 + 前端对话页 |
| 现状 | 有**可跑的脚本**（`scripts/qwen-image-makeup.ts`，26 KB）但**没接进服务** | 写本节时前后端**完全空白**；✏️ **后端已完成**（`src/modules/agent/`，阶段 2，2026-09-16），**前端对话页仍空白** |
| 不确定性 | 中（网络抖、审核未知） | 高（LLM 行为不确定、烧钱、demo 现场翻车的首要风险源） |
| 可否独立验收 | ✅ ~~一次性表单路径即可验收~~ **见 §8.1：这条路已冻结，不再是验收场** | ✅ 见 §12 |

**结论**：A 不做完就做 B = 空中楼阁。排期上 A 必须先行，且 A 自己就能交付价值（现有表单先用上真图）。

> ✏️ **2026-09-16 修订（§8.1）**：上面这段"排期"的**结论仍然成立，但落法变了**。
> "A 先行"依旧——只是 A 做完之后**不再接给现有表单**，而是接给 agent（阶段 3）。
> 因此 §8.1 记了一笔代价：**"现有表单先用上真图"这条早期收益被放弃了**，
> 换来的是"引擎的第一个消费者就是最终消费者"，少接一次线、少一套以后要拆的适配。
> 原文保留不删，是因为它是当时真实的分工理由；**要照它排期的话，先看 §8.1。**

## 4. ★ 核心约束：身份保真 → **LLM 不许写提示词**

这是本文唯一一条**已经花过钱**的结论，出处是 `server/scripts/README.md` 记录的 2026-09-15 三次真实调用
（输入同为 `scripts/assets/face-local.webp`，同 `seed=42`）`[文档原文]`：

| 那次用的提示词 | 出图结果 | 身份 |
| --- | --- | --- |
| 妆面稿（owner 给的 `prompts/look-sheet.txt`，逐字） | 1024×1024、白底裸肩、黑长直发——**图上每一句都兑现了** | ❌ **完全不是本人** |
| 妆面稿 + `--keep-identity` 锚句 | 又一张漂亮人像 | ❌ **锚句拉不住稿子里的构图/背景/裸肩条款** |
| `--template --occasion date`（**只说妆，不说构图**） | 妆效很淡，更像磨皮 + 提气色 | ✅ **是本人**——围巾、发型、脸型都对得上 |

> 原文档的结论句：**"身份丢不丢，不取决于模型能不能编辑，而取决于提示词里有没有『重摆构图 / 换背景 / 换服装』的条款。"**

### 4.1 这条结论推出来的设计

**如果由 LLM 自由撰写提示词，它会写出什么？** 这不是猜测——把上面那份 owner 手写的妆面稿
（一个**人类专家**写的、目的就是"把妆说明白"的稿子）喂进去，模型就已经跑到"重画一个人"去了。
一个为了"让描述更丰富"而生成的 LLM 提示词，**只会比人写的更容易漂移到构图/氛围/服装**。

> ### ⚠️ 因此：**LLM 永远不产出 prompt 文本。**
> LLM 只许往一个**结构化槽位空间**（§6 的 `LookSpec`）里填**枚举值 + 数值**；
> 最终 prompt 由 `prompt-builder.ts` 这个**确定性、带版本、可单测**的纯函数生成，
> 模板里**固定内置**身份锚句与反向提示词，且**结构上不可能出现构图/服装/背景条款**。
>
> ⚠️ **2026-09-16 修正：上面这条是必要但不充分的，见 §4.4。**
> 砍掉构图条款后**人仍会漂**——漂移的**第二个来源是妆面描述里的几何词**
> （「放大感美瞳」「睫毛浓密卷翘且外眼角加长」「眼线向外拉长并轻微上扬」）。
> **模板还必须在措辞层面禁止形状描述**，见 §4.4 与 §6 的字段约束。

### 4.2 这条约束顺带买到的三样东西

它不只是为了保真，同时解决了三个独立的工程问题——这正是它值得做成硬约束、而不是"注意一下"的原因：

| 买到的 | 为什么 |
| --- | --- |
| **可回归** | 提示词是 `LookSpec → string` 的纯函数，能像 `describeScene` 一样写表驱动单测。自由文本做不到。 |
| **可做肤色夹具对照** | 红线 §13-3 要求"5 档肤色各自的通过率"这个口径**学术界没有现成的、得自己建**（`roadmap.md` §13-3）。自由文本下每次措辞都不同，5 档之间**不可比**；固定模板下差异只来自 `skinTone` 这一个变量，对照才成立。 |
| **可控成本面** | 提示词结构固定 ⇒ 出图方差小 ⇒ 返工少。按张计费的模式下这是直接的钱。 |

> run 1 与 run 2 复现了 `scripts/README.md` 的结论；run 3 推翻了 §4.1 的充分性；
> ★ **run 4 把原因隔离出来，并验证了 §6 的字段设计——它是本文最重要的一次实测。**

#### 4.4.1 修正一：漂移有**第二个**来源——妆面描述里的几何词

run 3 已经把构图 / 服装 / 背景条款**全部砍掉**，人**仍然漂**。剥剩的那些词是原因：

> 放大感美瞳 · 睫毛浓密卷翘且**外眼角加长** · 黑色眼线向外**拉长**并轻微**上扬** · 深灰棕色放大感美瞳，较深外环

**这不是色与质地的描述，是几何描述。** 模型照办了——眼睛变大、外眼角上扬、鼻唇跟着被重画。

> ★ **所以模板还必须在措辞层面禁止形状描述**，不只是禁止构图条款。
> §4.1 那句「结构上不可能出现构图/服装/背景条款」**是必要但不充分的**。

**落进 §6 的字段约束**（这是本文最该照做的一条）：

- `tone`（色）/ `finish`（质地）/ `intensity`（浓度）三类字段**天然安全**——run 3 里表现好的
  正是底妆与腮红这两段纯颜色描述。
- **任何几何字段都是高风险**。§6 现在给 `brow` 留了 `shape: BrowShape`——**它和 run 3 翻车的词同类，要重新评估**。
- ★ **「放大感美瞳」这类眼型诉求，按现在的 `LookSpec` 根本没有地方放**。
  按现状它会被 agent 塞进自由文本字段——**那就等于把 §4.1 的约束开了一个后门**。
  **要么给一个受控的枚举槽位，要么明确不接受这类诉求**，不许留自由文本兜底。

#### 4.4.2 修正二：负向约束在这个模型上**不可靠**

run 1–3 的 prompt 里都写了「**不要磨皮**，不要改变肤色深浅」，反向提示词里也有「过度磨皮」。
**三次输出全部重度磨皮**，run 3 最严重。

> **锚句与反向提示词是建议，不是护栏。** 它们能降低概率，不能保证结果。
> 这条对 §5.2 的 `prompt-builder` 有一个直接后果：**别把身份保真的全部重量压在措辞上**，
> §12.1 的「身份保真」必须**实测打分**，不能因为"模板里有锚句"就默认通过。

#### 4.4.3 ★ run 4：漂移源被隔离，**§6 的字段设计得到验证**

**run 3 的结论（"越具体越不像"）是错的——那是从一次混淆了变量的实验里过度推广出来的。**

run 3 相对 run 2 同时动了两件事：**① 描述详细度**（一句话 → 一整段）**② 几何词的有无**。
当时把账算在了 ① 上。**run 4 把 ① 固定住、只动 ②**：底妆 / 腮红 / 眼影 / 眉 / 唇五段全保留
（详细度与 run 3 同级），**只删掉几何词**：

| run 4 删掉的几何词 | |
| --- | --- |
| `自然平眉` 的「平」 | 眉形 |
| `黑色眼线向外拉长并轻微上扬` | **整句删** |
| `睫毛浓密卷翘且外眼角加长` | **整句删** |
| `深灰棕色放大感美瞳，较深外环，柔和放射渐变` | **整句删**（最大的一个） |
| `下眼尾深色晕染`、`唇线柔和` | 位置 / 轮廓 |

**结果：身份保住、妆效清楚可见、构图全在。**

> ### ★ 所以真实的形状**不是**"具体度 ↔ 保真"的滑块，是"**几何词 ↔ 保真**"的开关。
> **色 / 质地 / 浓度写得再细都不花身份。**

这直接验证了 §6 的 `LookSpec` 字段设计——`tone` / `finish` / `intensity` **三维不是巧合，它就是安全区**。
§4.1 提出的方案（LLM 只填结构化槽位、模板只输出色/质地/浓度）**至此从假设变成有实测支撑的方案**。

**仍然要留的两条余量**：

- **单样本。** 四次各一张，`n=1`。颜色/质地的安全区在 5 档肤色、不同光线下是否同样成立，
  **本文没有数据**——那正是 §12.1 要建的口径。
- **§4.4.2 的磨皮问题没有被解决。** run 4 的皮肤仍然偏光滑。删几何词解决的是"五官漂移"，
  **不解决"磨皮"**——那是另一个独立的、仍然打开的问题。
- **§12.1 的两项指标仍要成对测。** run 4 说明"成对"不会永远冲突，但**不代表可以只测一项**。

## 6. `LookSpec` —— 层 A 与层 B 之间**唯一**的契约

```ts
// makeup/domain/entities/look-spec.ts
interface LookSpec {
  occasion: Occasion;                                   // 复用 shared 枚举
  base: { coverage: 1..5; finish: Finish; warmth: -2..+2 };   // 底妆
  zones: {
    lip:       { tone: ToneKey; finish: Finish; intensity: 1..5 };
    cheek:     { tone: ToneKey; finish: Finish; intensity: 1..5 };
    eyeshadow: { tone: ToneKey; finish: Finish; intensity: 1..5 };
    brow:      { shape: BrowShape; intensity: 1..5 };   // ⚠️ 几何字段，见规矩 5，待重估
  };
}
```

> ⚠️ **2026-09-16（§4.4.1）：前三行的 `tone/finish/intensity` 是安全的三维——
> 色、质地、浓度。它们是 §4.4 实测里唯一没有推动五官漂移的那类描述。
> 而 `brow.shape` 与「放大感美瞳」「外眼角加长」同属几何描述，是 run 3 翻车的同类，必须重新评估。**

四条设计规矩：

1. **枚举全部定义在 `shared`**（`roadmap.md` §2 的"枚举只定义一处"）——
   `Finish` / `ToneKey` / `BrowShape` 加进去要同步 zod schema → validator → `MockEngine` →
   `narration` → 前端 chips → 测试，**一处不能漏**。
2. **`Finish`（satin / matte / glossy）正是 `roadmap.md` §6 那条"阻塞自建路线"的待办**，
   原文写着"现有 `Look{style,palette,zones}` 没有任何地方放 satin/matte/glossy，
   而这恰恰是『像涂的 vs 像染的』的分水岭"。本次顺手补上，**不是新需求**。
3. **`LookSpec` 是引擎私有契约，不是新的契约层。** 它可以投影成 `Look`（对流水线仍不透明），
   也可以投影成 `MakeupZone[]`（归一化坐标，供前端 CSS 预览）。**不要让它泄漏进 `JobView`。**
4. **色板必须按 `skinTone` 走，不许 LLM 自由发挥。** 这是红线 §13-3 的落法——
   该节已从"直觉"升级为**有引用的论据**（ICCCV 2026 偏差审计，DOI `10.1145/3810417.3810425`，
   结论是 Black-presenting 脸退化最严重、且出现**非预期肤色漂移**）。
   **`LookSpec` 的合法取值空间本身就要按 `skinTone` 收窄**，而不是生成完再检查。
5. ★ **（§4.4.1 新增，最高优先）字段必须区分"色/质地/浓度"与"几何"。**
   前三维安全；**几何维度（形状、大小、拉长、上扬、浓密、放大）是 §4.4 run 3 实测到的漂移来源**。
   > ★ **§4.4.3（run 4）已验证这条：只留色/质地/浓度时，身份保住且妆效可见。**
   > 也就是说 `tone` / `finish` / `intensity` 这套字段**不是待验证的设计，是有实测支撑的结论**。
   规矩：
   - 新增字段前先问：**它描述的是颜色/质地/浓度，还是形状？** 是形状就默认拒绝。
   - **不许留自由文本字段兜底**——「放大感美瞳」这类诉求目前无处安放，
     一旦开了自由文本口子，§4.1 的约束就形同虚设。
     **要么给受控枚举，要么明确告诉用户这类诉求不支持。**
   - `brow.shape` 是现存的例外，**重新评估后再保留**。

### 7.3 harness 的形状：**模仿 Claude / DeepSeek 的八条**，不是抄代码

用户原话是"agent harness 可以模仿 deepseek 或者 claude 的代码"。落到工程上，
**值得模仿的是形状，不是源码**——下面是那八条，逐条给出"为什么这条重要"：

1. **一个循环，两个出口。**
   `tool_use` → 执行 → 回填 → 再循环；`end_turn` → 结束本轮、交还用户。
   ★ **`ask_user` 不是工具**——它就是"循环结束"的另一种形态。
   把它做成工具是常见错误：会导致模型"问一个问题又自己答了"，且无法与真正的终止区分。
2. **`messages[]` 是唯一状态。** 可持久化、可重放、可测试。
   **不要再起一套平行的状态机**——那正是本仓库 2026-09-10 删掉 `understanding` 模块的错误形状
   （`roadmap.md` §4："那个模块的全部内容是一个 `sleep` + 一次转发 + 一个只能拨到 mock 的开关"）。
3. **工具 = 名字 + JSON Schema + 描述 + handler**，注册表驱动。
   ★ **工具描述是给模型看的 prompt，是产品的一部分**，要按文案对待、要有人看、要能改。
4. **工具错误不抛穿循环。** 转成模型能读懂的 observation 回填，由模型决定重试还是换路。
   生图超时、key 失效、审核拦截都会走这条；**抛穿循环 = 用户看到一个 500，而不是一句"那张图没出来，我换个方式再试"**。
5. **预算守卫**（见 §10）。没有这个护栏的 agent 不能上线。
6. **流式事件协议**：`text_delta` / `tool_start` / `tool_end` / `turn_end`，走 SSE。
   前端要能看到"正在查衣橱…"——**7 秒的生图如果没有任何中间反馈，用户会以为卡死了。**
7. **上下文管理**：历史长了要截断。本项目的取舍很清楚——
   **最该留住的是 `LookSpec` 的当前值和用户偏好，不是全部聊天原文。**
   （这也意味着会话状态可以**很小**：一份 `brief` + 一份 `LookSpec` + 最近 N 轮。）
8. **两种 API 形状统一到一个内部 `Message`**：Anthropic 是 `content:[{type:'tool_use'}]` +
   `tool_result` 回填；OpenAI / DeepSeek 是 `tool_calls[]` + `role:'tool'` 消息。
   内部类型一套，adapter 各自翻译。★ **这正是 `llm.ts` 端口存在的理由，也是"换供应商不改业务层"的兑现方式。**

> **不引外部 agent 框架。** 本仓库的既有立场很一致（`roadmap.md` §7："真要做也只是进程内文件化队列，
> 别引外部中间件"，红线 §13-5 同口径）。上面八条加起来是**一个循环 + 一个注册表 + 一个预算计数器**，
> 引框架换来的抽象层，代价是**在唯一真正有风险的地方（工具错误处理、预算、身份保真）失去控制**。

### 7.4 ★ 核心取舍：`render_look` 仍需用户触发，但**没有中间预览**

> **⚠️ 2026-09-16 修订（owner 拍板）：砍掉 CSS 叠加预览，改成"通过对话直接生图"。**
> 本节原方案是"LLM 填 `LookSpec` → 前端用 zones 做 CSS 叠加秒出预览 → 用户看预览再点确认"。
> **该方案作废**，理由见 §7.4.1。下面是与 owner 拍板后一致的方案。

**方案**：

```
用户说话  →  LLM 填 LookSpec（免费，<1s）
          →  agent 用中文把这套妆"说"出来（文字确认，不是假图）
          →  用户说「出图」→ 真调 Engine（~6.5s + 一次计费）
```

> ⚠️ 最后一步的"用户说「出图」"**落地时改了含义**：确认必须是一次**HTTP 动作**，
> 不能是一句模型看得见的文本——否则模型可以替用户认为自己得到了同意。
> 见下面 §7.4.3。

**保留"用户触发"的理由**（这部分不变）：若每轮对话都自主生图 = 6.5s × N + 一路计费，
演示现场必翻车（红线 §13-1）。**贵的操作由人拍板**这条仍然成立。

#### 7.4.1 为什么砍掉 CSS 预览（两条，第二条是决定性的）

1. **它的保真度撑不起"预览"这个词**：`MockEngine` 的 `ZONES` 是**硬编码坐标**
   （`mock-engine.ts:83-89`，`唇 at (0.5, 0.47)` …），注释自己写明是"骨架约定为正面自拍照片"。
   非正面 / 非标准构图会**摆错位置**，看起来像 bug 而不是妆容建议。
2. ★ **它表达不了 `Finish`——而 `Finish` 正是 §6 特意加的那个字段。**
   色斑只有 RGB + opacity + blur 三个自由度，**没有"光泽"这一维**。
   于是会出现这个场面：用户和 agent 讨论了半天"要哑光不要水光"→ **预览上完全看不出来** →
   用户确认了一个**他根本没看见**的东西。**这比没有预览更糟**：它给了虚假的确认感。

> 顺带：`MakeupZone` 机制**本身不删**——`jobs` 那条一次性表单路径仍在用它（`ResultView.vue:190-195`），
> 只是**不再进对话路径**。

#### 7.4.2 砍掉预览的代价（要认，别假装没有）

| 代价 | 说明 |
| --- | --- |
| **每次迭代都是 6.5s + 一次计费** | 原方案里"唇再淡一点"是免费的，现在每次微调都要**真出图**。§4.4.3 那根"越具体越不像本人"的滑块，**每次调整都要花一次钱去试**。 |
| ★ **§10 `[I3]` 的渲染上限从"防滥用"变成"核心成本控制"** | 它不再是护栏，是**主要花钱闸门**。取值必须按"一次对话可接受的出图张数"来定。 |
| **用户在出图前只能靠文字判断** | 因此 **agent 的文字描述质量直接决定体验**——它必须把 `LookSpec` 讲成一句人话（"偏冷的玫瑰色唇、雾面质地、中等浓度"），这句描述就是"预览"的替代品。**这条要写进工具描述的设计里**（§7.3 第 3 条）。 |
| §12.2 的「免费轮次占比」指标作废 | 没有免费轮次了。改为测「**每次出图前的对话轮数**」——越低越好。 |

#### 7.4.3 ★ 2026-09-16 落地：确认**不是一次对话回合，是一条独立路由**

上面 §7.4 的方案里写的是"用户说「出图」→ 真调 Engine"。**这句话落地时被发现是有歧义的**，
歧义在于："用户说"是一句**模型能看见的文本**——那模型就可以在用户说「随便吧你看着办」的时候
自己认为"他同意了"，然后出图。**那样这道闸门就退化成提示词，而提示词不是闸门。**

**落地口径**（owner 拍板：工具 + 服务端确认回合）：

```
模型调 render_look
  → 工具返回 pendingConfirmation，服务端**不执行引擎**
  → events[] 以 tool_pending 收尾，stopReason = awaiting_confirmation
  → 前端据视图里的 pendingRender 弹确认框（文案来自 renderConfirmationSummary）
用户点「确认」→ POST /api/agent/sessions/:id/render
  → 服务端把**那一整轮**重放一遍，这次带 confirmation='approved' → 真出图
用户点「取消」/ 不发这条请求 → 缺省即 declined
```

**三个决定性的后果，都要认**：

1. ★ **闸门从提示词里搬到了代码里。** `confirmation` 只由「用户点了那条 HTTP 路由」设置，
   模型**无论怎么措辞都改不了它**——它连"用户已经同意了"这个谎都撒不出来，因为那不经过它。
2. ★ **待确认的那一轮，一条 `tool_result` 都不发，整轮重放。** 这是 harness 那条
   「同轮结果必须装进同一条 user 消息」的直接后果：一轮里但凡有一个 `tool_use` 悬着，
   就既不能发半批结果、也不能拆成两条。**代价是每个工具都必须可重入**
   （`patch_brief` 是覆盖写、`propose_look` 是纯函数、`list_cabinet` 只读——三者在重放时都安全）。
   ⚠️ **这是今后新增工具的一条硬约束**：写文件的、发消息的、计数的工具**不能**直接进注册表。
3. **确认框那句话只有一个来源**（`renderConfirmationSummary`），工具与视图都取它，
   免得"前端弹的话"和"后端以为用户看到的话"是两句。★ **文案里刻意没有金额**：
   §15.3 记着本项目**未核任何模型的价格**，编一个数字出来是拿没人验证过的数替用户做花钱的决定。

> **由此新增的接口面**：`POST …/render`（★ 全项目唯一会花钱的入口）、
> `POST …/photo`（照片在这一步才进得来）、`GET …/renders/:seq`。
> `POST …/render` **一个出图参数都不收**——要出的就是用户屏幕上那一套，
> 而它已经在会话里了；让前端再传一遍参数，就等于开了第二条能改变"出什么"的路径，
> 而那条路**绕过对话记录**。

> ✏️ **2026-09-16 二修（同日，真实模型实测之后）：出图从"模型提议的产物"改成"界面按状态自己摆的一条消息"。**
>
> **现象**（`qwen-turbo`，以及 owner 自己换成 `qwen-plus` 之后**同样**）：用户**两轮明确要图**，
> 模型一次都没调 `render_look`——
> 「生成图片我看看」→「需要我帮你生成成片看看效果吗？」；
> 「出图」→ 又把妆面讲了一遍 +「这套妆面你感觉怎么样？需要调整颜色、浓淡吗？」。
> 从服务端现读那个会话（`lookSpec` 有值、`hasFace: true`、`renders: []`、无待确认调用）：
> 界面上**既没有图、也没有那个确认框**，而上面那条链**只有这一个入口**。
> 用户的原话就是「对话界面也没有生成图片的选项」。
>
> **根因不是"模型不听话"，是上面那张图的布局错了**：这套设计自己写着
> 「闸门是那条 HTTP 路由、**提示词不是闸门**」（本小节第 1 条），可用户要图的那一下
> **仍然串在模型的提议后面**——而"提不提议"是**提示词级**的东西。唯一的串联点一断，整条路就没了。
> ★ 规则 6 在此之前已经改过四轮措辞（`v5` / `v5` 内并 / `v6` / `v7`），`v7` 那段自己立着规矩：
> **再复现就该改代码，不是第五次改措辞**——这次就是那次改代码。
>
> **改法**（owner 拍板：那条消息由**前端按状态自己摆**，**点一下直接出图、不要中间那一步**）：
>
> ```
> 妆面定了 + 照片有了 + 额度还有
>   → 前端在对话末尾摆一条消息：「要现在生成成片吗?…大约需要 7 秒,并按次计费。…」
>      + 按钮「确认生成」            ← 文案来自 renderConfirmationSummary（唯一一份，一字不加）
> 用户点它 → POST …/render（路由不变、仍不收任何出图参数）
>   · 历史里欠着一条 render_look → 入口 A：按 approved 重放（与今天一字不差）
>   · 没有欠账、条件齐          → 入口 B：服务端**代递**一条提议（id 前缀 `manual-`），
>                                  同一次请求里按 approved 跑完 → 图就在这一次请求里出来了
> ```
>
> **由此变了的四件事，都要认**：
>
> 1. ★ **界面上只剩一种出图入口。** 原来那张确认卡不再单独存在——它与新按钮合成同一条消息，
>    内容取 `pendingRender ?? renderOffer`（服务端保证两者互斥）。
> 2. ★ **提示词一个字都没改**（规则 6 正文与 `SYSTEM_PROMPT_VERSION` 仍是 `v11`）。
>    第 2 条「闸门在代码里」这次才算真的兑现：**"用户要图"这件事不再必须由模型转达**。
> 3. ⚠️ **这是"一次点击就花钱"。** 所以费用与时长必须在**点之前**看得见（那句话仍是唯一一份），
>    防误连点三道：出图期间按钮禁用 + 服务端**按会话的进程内 in-flight 锁** +
>    **出过这一套之后按钮改口叫「再生成一张」**。
> 4. ⚠️ **`POST …/render` 的 422 换了含义**：不再等于"没有待确认项"，
>    而是三个真实原因（缺妆面 / 缺照片 / 上一轮欠着的不是出图请求）外加一种并发连点（"正在出图"）。
>    ★ 沿用 §14 那条记录里的口径——**改写，不删**。
>
> **残留的洞（如实记，本次不关）**：响应在回程丢了、用户又点一次，服务端看到的是一个
> 「妆面照片齐、额度也有」的会话 ⇒ 那在它眼里是**正当的新请求**，会真出第二张。
> 关掉它要幂等键，而幂等键要在这条**"一个出图参数都不收"**的路由上**加客户端输入**——
> 不为这个洞破例。

## 8. 与现有 `jobs` 流水线的关系：**两条路并存，不许合并**

| | `POST /api/jobs`（现有） | `POST /api/agent/sessions/:id/messages`（新） |
| --- | --- | --- |
| 形态 | 一次性表单 → 异步任务 → **轮询** | 多轮对话 → **SSE** |
| 状态 | `JobRecord` 状态机（`queued→running→done\|failed`），步骤单调推进 | `messages[]` + 会话级 `brief`/`LookSpec` |
| 保留理由 | **demo 兜底 + 逃生门**（红线 §13-1） | 新体验 |
| ✏️ 当前状态（2026-09-16） | **冻结**：能跑、不投开发（**§8.1**） | **阶段 2 已完工**；出图在阶段 3 |

> ⚠️ 表里"**SSE**"写的是**目标状态**，不是现状。阶段 2 是"一轮跑完一次性返回"的普通 JSON；
> 响应形状已经造成事件流（`events[]`），阶段 3 只换传输、不换契约。理由见 `modules/agent/README.md`。

三条边界：

1. **agent 的 `render_look` 直连 `Engine` 端口 + `validateEngineResult` + `ArtifactStore`，
   不走 `jobs` 的 `JobRecord` 状态机。** `jobs` 那套是"一次性异步任务 + 轮询"的形状，
   硬塞进对话会拧巴——**同一个错误形状，本仓库已经犯过一次并删掉过**（`understanding` 模块，见 §7.3 第 2 条）。
2. **复用引擎而不复用流水线**：`Engine` / `validateEngineResult` / `ArtifactStore` 三个都是干净的端口或纯函数，
   直接复用；`RunPipeline` 是编排，**不复用**。
3. **一次性表单路径不许退化。** agent 挂掉（LLM 不可达、预算耗尽、审核拦截）时，
   用户必须还能走 `POST /api/jobs` 拿到图。**这是红线 §13-1 的具体落法，要写进验收。**

### 8.1 决策：`jobs` **冻结不删**，出图能力接到 agent 上（2026-09-16 拍板）

上面三条边界仍然全部成立，本节只钉**资源怎么投**：

- **`jobs` 冻结**：不删模块、不删路由、不删测试，也**不再往它投任何开发**。
  它从"并列的一条产品路径"退成**保险丝**——`[I7]` 因此继续成立（保险丝的前提就是它还在、
  还能跑），红线 §13-1 不动。前端可以把表单入口摘掉，**但后端路径留着**，
  演示当天 LLM 翻车时手动走得通。
  > ★ **为什么没删**：删了 `[I7]` 就作废，而 agent 是失败模式最多的那条路
  > （LLM 不可达 / 预算耗尽 / 拒答 / 超时四种，`agent-loop.ts` 里各有一条收束分支）。
  > 把确定性的那条删掉、只留会挂的那条，正好把红线 §13-1 的风险倒过来放。
- **出图能力（`prompt-builder` + `QwenImageEngine`）接到 agent 上**：阶段 1 与阶段 3 的引擎部分合并，
  先做 `render_look` + 人在回路确认。**走通后 agent 就是唯一的产品路径。**

  ⚠️ **这条决定有一处代价，写下来免得下次当成疏漏**：阶段 1 原来的验收口径是
  「**一次性表单路径出真图**」——那是一条现成的端到端验证。`jobs` 一冻结，这条口径就没了
  （表单路径虽然还能跑，但它跑的是 mock 引擎，不再是新引擎的验证场）。
  阶段 1 的验收因此换成：**`buildPrompt` 硬断言绿 + 引擎的 record/replay 夹具绿**
  （见 §14 改后的那一行）。**这是"先接 agent"多付的那一笔。**

  > ★ 注意引擎本身**与消费者无关**：`prompt-builder` 与 `QwenImageEngine` 都落在 `makeup` 模块内，
  > 不 import agent。上面说的"接到 agent 上"指的是**谁当第一个调用方**，
  > 不是指引擎要依赖 agent——依赖方向仍然是 agent → makeup。

## 9. 会话与数据（隐私）

红线 §13-4：**"现场临时自拍采集最小化、即用即删、口头同意即可；不做任何真实用户数据的留存与上传。"**

对话式会改变风险的形状——**一次性表单是"用完即忘"，对话是"照片要留到会话结束"**。所以：

| 项 | 决定 | 理由 |
| --- | --- | --- |
| 照片存放 | ✏️ **已定（2026-09-16）：复用 `assets` 的 `ArtifactStore`**，不新写第二套。经 `SessionArtifacts` 端口 + 组装根那层适配（§7.1） | 与 `jobs` 现存做法一致，不新开隐私面。★ 于是 `jobs` 与 `agent` 用的是**同一个存储实例** |
| **会话 TTL** | ✏️ **已定**：**24 小时**（`AGENT_SESSION_TTL_HOURS`，可配），由 `PurgeExpiredSessions` 用例 + 组装根的定时器（每小时扫）执行，**到期真删** | 新增的风险点。一次性表单没有这个面 |
| 会话结束 | 删照片 + 删中间产物 | 兑现"即用即删" |
| 会话内容 | 存服务端（**不是**浏览器 localStorage） | 因为 `render_look` 要读照片；与 `roadmap.md` §14 那条"数字妆造间存哪"的**取舍不同**——那条讲的是**生成历史**（可本地），本条讲的是**进行中的会话**（必须服务端） |
| 归属 | 客户端显式传 `userId`，无令牌 | 沿用红线 §13-5，本文字不改变它 |

> ★ **两条要分清的"存哪"**：`roadmap.md` §14 的"数字妆造间"（历史作品）**建议本地**，那条建议不受影响；
> 本文的"进行中的会话"**必须服务端**，因为它握着用户照片和工具调用的中间态。
> **不要把二者合并成一套存储。**

> ✏️ **2026-09-16 落地后记（两条已知缺口，别当它们不存在）**：
>
> **① 重启之后的孤儿文件 —— ✏️ 已关（2026-09-16）。** 原先 `[I8]` 的清理是**按会话记录去找文件**的，
> 而会话是**内存**实现，于是进程一重启，上一次留在盘上的照片**没有任何会话能认领，也枚举不到**。
> 处置是让用例扫**两遍**：第一遍照旧按记录 findAll，**第二遍反过来从盘上列目录**，
> 凡是没有会话认领的就真删（`SessionArtifacts.listStored` → `ArtifactStore.listIds`）。
> 第二遍**不需要判年龄**——会话记录是通往一份存储的**唯一**路径，
> 认领不到的 id 就是永久不可达，留一秒都是白留（也避开了跨平台不一致的目录 mtime 语义）。
> ★ 这条能提前关掉，是因为**隐私承诺不该挂在功能排期上**：重启是常规事件，
> 而 `[I8]` 承诺的是"最多留 24 小时"，不是"最多留到会话落盘做完"。
> 会话落盘之后第二遍仍然留着，角色从"补缺口"变成**兜底自愈**。
> ⚠️ 源码里那句 `listStored` 的失败**只warn不抛**（清理任务要能重复跑），
> 所以测试里那个假存储**必须实现它**，否则第二遍会**静默不跑**——这个坑踩过一次，已写进测试注释。
> ★ 顺序上，`PurgeExpiredSessions` 刻意**先删文件再删记录**：
> 反过来的话，删记录成功、删文件失败，这个会话就**再也没人认领了**——
> 盘上留下一张永远删不掉的真人照片；而反过来的失败只是"这次没删干净"，下次扫描能自愈。
>
> **② ★ 引擎自己的中间产物（接线时才发现，比上一条更隐蔽）。**
> 引擎把成品写在 `<DATA_DIR>/engine-out/<时间戳>.png`（`image-engine.ts`），
> **那张图就是用户的脸上了妆**，而它**不归任何会话**——清理任务永远枚举不到它。
> 于是"会话那份删了"并不等于"盘上没有了"。**处置：`agent` 收编一张图之后立刻把引擎那份删掉**
> （落在 `src/session-artifacts.ts` 的 `putRender`，那是"收编"这个动作该管的事，且有测试）。
> ⚠️ **这道删除必须带边界（只删落在引擎输出目录里的），而边界是踩出来的**：
> `MockEngine` 返回的"产物"**就是输入照片自己**（`resultFilePath: input.face.filePath`），
> 而照片在 `inputs/<sid>/face/` 下——无边界的删法**第一次出图就会删掉用户上传的照片**，
> 会话里 `faceRef` 还在、第二次出图就解析到空气。★ 这条记在这儿的价值是：
> **"删一个文件"这种动作，它的判据必须是"这文件属于谁"，不能是"它是不是刚从引擎那儿来的"。**
> ⚠️ **但 `jobs` 那条路不走这个适配器**，它的中间产物照旧只增不减。`jobs` 已冻结、且 `qwen` 下
> 表单路径本来就不可用，**所以当前没有真实泄漏**——但**只要表单路径重新能用，它立刻变成一笔隐私债**。
> 这一条记在 `modules/makeup/README.md` 的待办里，那里也写着那个配置坑：
> **`MAKEUP_FIXTURES_DIR` 不能指到 `engine-out`**（收编会连花钱录的夹具一起删掉）。

>
> - **`[I3]` 取 3，理由不是省钱。** 一张图才几分钱，3 张也谈不上成本。真正的理由是 §7.4.2 说的那件事
