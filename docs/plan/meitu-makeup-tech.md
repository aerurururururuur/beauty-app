## 1. 结论速览

| 问题 | 结论 |
| --- | --- |
| 美图的妆是贴图还是生成？ | **两套并存**。主流「美妆」= 贴图素材叠加；「仿妆」= GAN 生成式迁移 |
| 贴图线是不是少数派？ | 不是。它是**端侧实时 + 云 API 的主力**，有官方素材规范文档 |
| 眉毛怎么处理？ | 贴图线里是**独立素材品类**（`mmy`/`mmz`，**左右分开导出**）；仿妆线里是**独立判别器** `D-Eyebrow` |
| 有没有「不替换、只增强」的路线？ | **有**。`eyebrow_deepen`（眉毛增强，0–100）与 `eyebrow`（替换式）**并列独立** |
| 2024–26 转扩散了吗？ | 美图整体转 MiracleVision，但**妆造未见扩散**。截至 2026-09 文档仍是素材 ID 体系 |
| 学术界的妆容迁移管眉毛吗？ | **基本不管**。BeautyGAN 主动把眉毛从眼影 mask 里剔除；PSGAN/CPM/SSAT 全文 `eyebrow` 出现 0 次 |

## 2. 两套系统

| | 主流「美妆」 | 「仿妆 / AI 仿妆」 |
| --- | --- | --- |
| 范式 | **贴图素材叠加** | **GAN 生成式迁移** |
| 载体 | Photoshop 绘制的 PNG 素材 | MakeupGan 模型 |
| 运行位置 | 端侧 `MTARSDK`（OpenGL 实时）+ 云 `v3/makeup` | 云端 GPU `v1/aimakeuptransfer_gpu` |
| 入参 | `makeupId` + `makeupAlpha` | **用户图 + 模特图**两张 |

`[二手·官方]` MakeupGan 官方技术文的判别器为 `D-Eyebrow` / `D-Eye` / `D-Lip`；
云端仿妆接口按部位暴露 `eyebrow_alpha` 等透明度。
MakeupGan **没有论文**——顶会检索里美图在这条谱系上是缺席的 `[二手]`。

> 注：BeautyGAN / PSGAN / CPM / SSAT **均非美图工作**（分别是北航+SenseTime、北航+CASIA+NUS、
> VinAI、武汉理工）。其中 PSGAN 真实归属是 **CVPR 2020**、CPM 是 **CVPR 2021**、
> SSAT 是 **AAAI 2022**。`[一手·读原件]`

## 3. 主流美妆线 = 贴图（一手证据）

**`doc?id=167`《标准妆容》原文：**

> 1.3 坐标 x,y 和宽高调节：**在 Photoshop 上绘制的妆容**，可能在实时渲染时存在些许误差
> 1.4 **叠加模式：根据 Photoshop 上图层的叠加方式**，选择相应的叠加模式

另有专文《叠加模式》`doc?id=183`。`doc?id=175` 要求素材基于 **1000×1500 标准脸图**在
Photoshop 里绘制、按图层导出。

**3D 路径同样是贴图**——`doc?id=179`《3D 重建素材》提供 `uv.zip` + `Face.obj`，
要求设计师**对着 UV 图画眉毛素材**：

**结论**：`关键点锚定 + UV 贴图叠加` 就是美图主力产品线的架构，
**与 `tespro/` 现有 brow 模块同构**。这条路线本身不构成"做错了"。

## 4. 眉毛：独立品类，且左右分开 `[一手·官方文档]`

`doc?id=175` 的部位命名表（摘）：

```
右眉毛 mmy    左眉毛 mmz    右眼影 yyy    左眼影 yyz
右眼线 yxy    左眼线 yxz    右睫毛 jmy    左睫毛 jmz
```

原文：

> 右眉毛命名规范为 mmy……不要使用 mm1y，mm2y 等命名

两条可直接借鉴的工程口径：

1. **眉毛不与眼影共用素材体系**——呼应 `brow-rendering-refactor.md` §0.2.3：
   我们此前把 `peak` 的上限借用了眼影/腮红的量程，恰好抹掉了这个区分。诊断方向是对的。
2. **左右眉是两张独立素材**，不对称在**素材层**解决。
   对照 §11.2/§11.4：我们认定"本 UV 布局下生成器里无解、需 shader 每侧变换"，
   而美图是**在素材层分开做**的。这条路值得重新评估。

## 5. 关键：`eyebrow_deepen`——存在「不替换」的路线 `[一手·官方文档]`

`doc?id=348`《美妆技术》参数表，眉毛有**两个并列且独立**的入口：

| 分类 | 部位名 | 参数 | 取值 |
| --- | --- | --- | --- |
| 妆容调整 | **眉毛** | `eyebrow` | 预设 id（示例 `"jianmei"` 剑眉）+ `color` + `alpha` |
| 妆容调整 | **眉毛增强** | `eyebrow_deepen` | **0～100，默认 0** |

`_deepen` 是一个家族：`facial_deepen` / `eyeshadow_deepen` / `lipstick_deepen` / `eyebrow_deepen`。

`eyebrow`（带形状 id + 颜色 + alpha）是**替换**——与我们正在做的事同类。
`eyebrow_deepen` 是**对原生眉区做增强**。

`[推断]` 文档未写机制。"独立于带 color/alpha 的 `eyebrow`" + `_deepen` 横跨多部位这两点，
指向**对已分割区域做局部加深/提对比**，而非叠加素材。**此条未证实。**

**但"眉毛"与"眉毛增强"是两个并列功能这件事本身是硬的**——它说明商业产品里
"替换式上妆"不是唯一形态。

### 5.1 "美图是不是先把图里的眉毛抠出来再变换？" `[一手·厂商页面]`

这是个自然的猜想（替换式在浓密原生眉上盖不住，那不如直接用原图里的眉）。
查了能查到的一手来源，**不支持这个猜想**：

- **美图魔镜 MeituGenius 产品页**（`mirror.meitu.com/feature_tech`，2026-09-14 直取）原文：

  > "By precisely locating **118 facial points**, it's able to support single item trials…
  > In addition, this exclusive AR technology allows for **layering and mixing texture,
  > shade and other effects** in order to replicate the actual visual effect of makeup,
  > and supports both thick and thin application of virtual makeup."

  → 关键点 + **贴图分层混合**。全页 `eyebrow` 只出现一处，在
  "brow shape / eyebrow thickness" 那句 **面部属性分析**里（用于推荐妆效），
  **与渲染无关**。**没有"提取原生眉"的表述。**
- **`eyebrow`（doc 348）本身**：预设 id + `color` + `alpha` —— 这就是贴图替换的口径。
- **检索 MT Lab 的眉毛增强 / 眉毛分割论文：没有找到**。`[实测·检索结果]`
  —— 这是"没找到"，不是"不存在"。

`[推断]`：美图的**眉笔试妆（魔镜 AR）是贴图**；`eyebrow_deepen` 是并行的第二条路。

> §5.2 推翻了本节"机制仍未公开"和"没有一手证据"这两句。** 本节保留原样，作为

### 5.3 端侧实证（二）：`Color` 模式的实装与它的边界 `[实测·静态符号分析]`

> 修正 §5.2 末句：**实现细节是拿得到的**。着色器源码以**明文串**躺在 `.rodata` 里
> （`libmtImageKit.so` 共 **1025** 段内嵌 GLSL，见 §5.7），本来就是可读字符串。

> ⚠️ **标题已于 2026-09-14 收窄。** 原标题是「上妆合成用的就是 W3C 的 `Color` 模式」——
> 那个说法**过度概括**。按部位扫完之后（§5.5 / §5.14）：**`Color` 只对「唇的材质那一路」
> 成立**；腮红是乘性染色、眼影是纯 alpha-over、眉/眼/唇加深是纯减法压暗。
> 本节讲的是 **`Color` 这条公式本身确实存在、而且逐字合规**，**不是**"美图上妆用 `Color`"。

**结论：美图**唇的材质那一路**的合成，与 `tespro/learn/blend/` 里那个 `color` 模式是同一条公式。**

W3C《Compositing and Blending Level 1》对非可分离模式的定义：

```
Lum(C)        = 0.3·R + 0.59·G + 0.11·B
Color(Cb, Cs) = SetLum(Cs, Lum(Cb))      // 取 Cs 的色相+饱和度，明度换成 Cb 的
SetLum(C, l)  = ClipColor(C + (l - Lum(C)))
```

`[代码事实]` 美图实现与上式**逐项同形**：`Lum` 权重就是 `vec3(0.3,0.59,0.11)`；
`ClipColor` 的两条回夹分支、`SetLum`、`ColorBlend` 均与规范一致。
其中 `ColorBlend(Cb, Cs) = SetLum(Cs, Lum(Cb))`，`Cb` = 底图、`Cs` = 妆色。
**这不是"类似"，是同一份规范实现。**

> ⚠️ **2026-09-14 更正本段的一处过度概括**：上文原先把 `SetSat` 也列进"与规范一致"，
> **是错的**。B 型（`0596`/`0605`）的 `SetSat` 是**线性缩放近似** `(C−n)*(s/d)`，
> 不是规范的 min/mid/max 三分支（详见本节末「唯一逐字合规的混合模式」）。
> **但这条更正不影响 `Color`** —— `Color(Cb,Cs) = SetLum(Cs, Lum(Cb))` **根本不用 `SetSat`**，
> 所以它仍是逐字合规的。受影响的只有 `Hue`。

对应的玩具侧代码是 `learn/blend/main.js:184`：
`c = mix(base, setLum(uColor, lum(base)), a)` —— **`setLum(uColor, lum(base))` 即
`SetLum(Cs, Lum(Cb))`。D1 玩具的 `color` 模式不是猜想，是美图实际发版的那条公式。**

#### 三处差异（其中一处是玩具侧的真缺陷）

1. **`[代码事实]` 玩具少了 `ClipColor`。** 规范的 `SetLum` 是「平移明度 → **回夹到色域内**」。
   `main.js:141` 写的是裸平移 `c + (l - lum(c))`，越界通道由 GPU **逐通道**裁掉，
   **裁掉就换色相了**。改法：照规范补上 `ClipColor` 的两条分支。
2. `[代码事实]` 亮度权重：玩具用 BT.601 的 `0.299/0.587/0.114`，美图用 W3C 规范字面的
   `0.3/0.59/0.11`。差约 0.0007，**可忽略**。
3. `[代码事实]` 美图在**非预乘的 straight RGB** 上做混合（先 `rgb/a`，混完 `*a` 预乘回去），
   器内注释给的理由是「避免半透明边缘脏色」。玩具直接读 `texture2D(uBase,uv).rgb`
   —— 底图若不是非预乘，半透明边缘会偏。

#### 为什么是 `Color` 而不是 `Hue`（有产品口径注释）

单色版着色器的 `blendMode` 上挂着两行产品口径注释：选 `Color` 是因为它"对任意底图都
强制取材质的色相+饱和度"，满足"各种颜色都要上色且不偏色"；而 `Hue` 在**低饱和（"灰度"）
底图上会退化成 `Color`**。代码里真有这条兜底：

```
if (Sat(Cb) < 1e-5) blended = ColorBlend(Cb, Cs);   // 底图近灰时，Hue 退化为 Color
```

→ **这正压中 `brow-rendering-refactor.md` §0.2 那类用户：底色越淡，越必须用 `Color`。**

同一个库里另有三份拷贝实现同样四种模式（色相/饱和度/颜色/明度），但走的是
**RGB↔HSB 逐通道互换**；而 `颜色` 这一档被单独分支出去用 W3C 实现（分支上留了短注释
「颜色用这个混合」）。`[推测]` 那三份 HSB 拷贝是踩过色偏/发灰之后的遗留，把 `颜色`
一档切给规范实现是补丁 —— 能证实的是「两条实现并存 + 颜色档被切走」这个**结构**。

#### `Color` 是全语料唯一一档**逐字合规**的混合模式

`[实测]` 把带 `SetLum`/`ClipColor` 的段按 md5 去重后，「5 段」其实是**2 份实现**：
`0545`=`0563`=`0570`（A 型，四档 `blendType`）、`0596`=`0605`（B 型，两档 `blendMode`）。
同一份文本在多个库里各躺一份是静态库的常态 —— **段数不等于种数**，统计前必须去重。

B 型比 A 型"更像规范"：它有完整的 `SetSat`，且 `HueBlend` 写成
`SetLum(SetSat(Cs, Sat(Cb)), Lum(Cb))`，与规范同形。**但它的 `SetSat` 是近似**：

```
vec3 SetSat(vec3 C, float s) {
    float n = min(C.r, min(C.g, C.b));
    float x = max(C.r, max(C.g, C.b));
    float d = x - n;
    if (d < 1e-6) return vec3(0.0);
    return (C - n) * (s / d);      // 线性缩放，不是规范的三分支
}
```

器内注释自己写着「近似保留色相」。规范的 `SetSat` 对 min/mid/max **三分支分别处理**
（保住中值通道的相对位置），线性缩放只是把 `[n,x]` 拉成 `[0,s]` —— 中值通道被一起缩放，
**色相只是"近似"不变**。

→ 一个干净的推论：**`Color(Cb,Cs) = SetLum(Cs, Lum(Cb))` 是唯一不需要 `SetSat` 的模式，
因而也是全语料里唯一一份逐字合规的 W3C 混合。** `Hue` 反而是近似的 —— 因为只有它要
`SetSat`。这条**不是**"美图偏爱 `Color`"的论据，是"`Color` 恰好是唯一能不做近似就
实现的非可分离模式"。

`[实测]` 两句关键注释直接到 `libmtImageKit.so` 里 `grep -a` 原核过
（`灰度底图上色` / `效果发灰` 各命中 **2** 次，与该段的两份拷贝数吻合）——
**注释确实在二进制里**，不是我的提取脚本带进来的。

#### 直接回答：「美图是用 `color` 还是 `multiply`」

**都用了，而且不是一道选择题 —— 它们在不同的通路上。** `[代码事实]`

| 通路 | 实现 | `multiply` / `color` 在里面的位置 |
| --- | --- | --- |
| 可分离模式 | `PSBlendLutTexture`，16 档 2D LUT，索引 `vec2(source, destination)` | **`multiply` 是 16 档之一**（§5.8），未见默认或主力证据 |
| 不可分离 · A 型 | `blendType` 四档，仅 `==3` 走 W3C | **`color` 是被单独 special-case 的那一档** |
| 不可分离 · B 型 | `blendMode` 两档（Hue/Color） | **`color` 是其中一档，带产品口径注释** |
| 各部位写死 | §5.14 | 腮红那一路用的正是 **`multiply` 的核**（`底图 × 比例`） |

两条**不要**得出的结论：

- ❌「美图用 `multiply`」—— `multiply` 只是 16 档之一，无证据表明是主力。此前报的
  「`D*S` 出现在 **31 段**」这个数**被分派器污染了**：分派器把 16 个核写在同一份
  shader 里，一算就是 16 段。**扫出来的段数不等于真的种数**（同 §5.12b 的教训）。
- ❌「美图上妆用 `color`」—— 见 §5.5 与 §7 第 9 项：`Color` 只对**唇的材质那条路**
  成立；**部位层是各写各的**。

#### 另一个独立模式：YUV 空间里的 Luminosity

另捞到一个在 YUV（BT.601 系数）里**只混 Y、U/V 全取底图**的着色器。`mask.y = 1` 时
结果 = 取"妆的明度 + 皮肤的色度"，即 W3C 的 **Luminosity** —— 方向与 `Color` 相反。
用途应是**承载明暗的材质层**（高光/修容/3D 材质）而非平涂色层。**用于上妆的仍是 `Color`。**

> ⚠️ 边界同 §4：仅静态字符串/符号分析。
> 本节描述的是**机制**（W3C 公开规范）与**结构**（哪一档走哪条实现），
> **不摘录美图的着色器源码**。文内引的两句短注释是作为"产品口径确实存在"的证据引用。

### 5.4 眉部增强到底做了什么运算 `[实测·静态符号分析]`

§5.2 路线 3（局部增强）那把着色器拿到了。**它和眼影/唇走的是不同的运算：**

| | 门控（相乘的各项） | 运算 |
| --- | --- | --- |
| 眼影 | `wakeMask.b × sharpenAlpha × eyesMask × 饱和度门控 × (1-isMouth) × skinMask` | 保色相的降饱和重建 |
| 唇 | `wakeMask.r × sharpenAlpha × eyesMask × 饱和度门控 × isMouth × skinMask` | 同上 |
| **眉** | **`wakeMask.r × eyebrowSharpenAlpha × (1 - eyebrowSkinMask)`** | **`color - delta × 0.25`，纯减法压暗** |

三条要点：

1. `[代码事实]` **眉毛没有 `skinMask`，也没有饱和度门控。** 唯一的空间门是
   `(1 - eyebrowSkinMask)` —— "**不是皮肤的地方**"，即毛发。§5.2 那句推断到此升级为代码事实。
2. `[代码事实]` `delta = 0.6 × min(R,G,B)`，效果是减去 `delta × 0.25`。
   `[推测]` 因为 `delta` 正比于最暗通道，**本来就很深的毛发几乎不动、偏浅的毛发被压最多**
   —— 读起来像"补毛量"而不是"整体调暗"。**未证实。**
3. `[代码事实]` 器里有一个声明后从未使用的变量（`ratio`）。无害死代码，
   但它是"这段是迭代出来的"的一个旁证。

> **对 §7 第 2 项那条待拍板问题的含义**：美图的"眉毛增强"在算术上就是
> **"对已判为毛发的像素做小幅压暗"**，不是什么高级算法。
> **这条路的门槛在分割（毛发/皮肤），不在运算本身。**

### 5.5 合成策略是**分层的**，不是一个模式打天下 `[实测·静态符号分析]`

把全量内嵌 GLSL 扫完之后（§5.7），能证实的结构是**合成策略按部位分派、各管一摊**：

| 部位 / 用途 | 合成方式 | 依据 |
| --- | --- | --- |
| **唇**（材质/珠光那一路） | **W3C 非可分离 `Color`** | §5.3，`SetLum(Cs, Lum(Cb))` |
| **腮红** | **底图 × 颜色比例**（乘性染色） | §5.14，`targetColor = 底图 × ratio` |
| **眼影** | **alpha-over 平色** | §5.14，`mix(结果, 颜色, 掩膜alpha)` |
| **眉 / 眼 / 唇 加深** | **纯减法压暗** | §5.4，`color − 0.6×min(R,G,B)×0.25` |
| **眉弓填充 / 修容** | **soft-light 加高光** + 保纹理磨皮 | §5.14 |
| **通用效果层** | **纯 `mix(src, effect, a)`**，即 alpha-over | `s_texture` / `e_texture` / mask 那一族 |
| 通用图层合成 | Porter-Duff source-over + 反预乘 | `lastCurrentTexture` / `blendTexture` |
| 材质·光泽层（珠光/闪片） | **闪片三层视差 + 亮度重映射 + 高光抬升** | §5.11（2026-09-14 已取到源码） |

> ⚠️ **2026-09-14 修正本表第一行。** 此前本表把「上色」整行写成 W3C `Color`，
> 那只对**唇的材质那条路**成立。按部位扫完之后（§5.14）：**腮红是乘性、眼影是 over、
> 眉是减法压暗。** `Color` 不是通用上色方案，是唇那一路的选择。
> —— 结论方向不变，但**不要把「唇用 Color」推广成「美图上妆用 Color」**。

> ⚠️ **这修正了一个容易过度推广的印象。** 旧库 `libmtimage-jni.so` 里确实有整套
> Photoshop 可分离混合模式（见 `learn/blend/README.md`），但**"美图有这个库"
> 不等于"美图的上妆用这些模式"**。现代引擎里：上色那一层用 W3C `Color`，
> 通用效果层干脆就是 alpha-over。
> **D1 的真正命题不是"公式库不够"，是"shader 读不到皮肤"。**
> 这一层发现把命题**收紧**了，不是推翻。

### 5.6 一条可直接抄的工程手法：色差保护 `[代码事实]`

通用效果层虽然用 `mix`，但**不是裸 `mix`**。`overlayMode` 那一族里：

```
maskAlpha   = smoothstep(0.05, 0.95, clamp(maskColor, 0.0, 1.0))
colorDiff   = abs(effectColor.rgb - srcColor.rgb)
diffValue   = max(max(colorDiff.r, colorDiff.g), colorDiff.b)
diffProtect = mix(1.0, 0.55, smoothstep(0.10, 0.28, diffValue))
blendAlpha  = clamp(maskAlpha * 0.975 * diffProtect, 0.0, 1.0)
result      = mix(srcColor, effectColor, blendAlpha)      // 输出 alpha 取 srcColor.a
```

三个动作，全都冲着"贴纸感"去：

1. **`smoothstep(0.05,0.95)` 软化 mask 边缘** —— 保留 mask 自身的渐变，把两端推实，
   避免硬抠边。
2. **`× 0.975`** —— 即使 mask 满、色差为零，**这层也永远到不了 1.0**。
   这是个刻意的天花板：**绝不完整替换皮肤**。
3. **色差保护**：`|effect − src|` 的通道最大值落在 [0.10, 0.28] 时，
   把强度从 1.0 降到 **0.55** —— **效果离皮肤颜色越远，就压得越狠。**

器内注释给出的理由是：**效果强时容易放大肤色的块面差异，所以用渐变 mask 与色差保护
弱化突变**（原文为中文，此处转述）。

> **含义**：美图针对"上妆显块、显假"这个病有**实装的对策**，而且是个便宜的补丁
> —— 与 `Color` 模式正交，可以叠在 `learn/blend/` 上单独试。
> `[推测]` 第 2 条那个 0.975 的天花板是为了让底图纹理在任何参数下都留一点，
> 但**这只是推测**，注释没写理由。

### 5.8 全局混合分派：**16 档模式，一张 2D LUT** `[实测·静态符号分析]`

`blendModeType` 取 **0..16 共 16 档**（源码里有越界兜底）。实现是**查表**，不是每次算公式：

```
除 13/14 外，全部走一张 2D 纹理（名字里带 PS 前缀）：
    结果.r = 查表(素材.r, 底图.r)
    结果.g = 查表(素材.g, 底图.g)
    结果.b = 查表(素材.b, 底图.b)
13/14 走解析式：按 Lum 在两张图之间取大 / 取小
```

**纹理名里的 `PS` 就是 Photoshop。** 这补齐了 §5.5 那条旁证的另一半 ——
可分离混合模式在美图里是**烘焙成 LUT** 的，运行时只查表。

> ⚠️ **一处观察到的命名与实现不符，只记录、不下结论**：13 档注释写「变亮」，
> 但调的是按 Lum 取**较小**值的函数；14 档写「变暗」，取的是较大值。
> 两个注释名与两个实现**正好互换**。
> `[推测]` 可能是命名笔误，也可能档位定义与直觉不同 —— **无证据，不写成 bug。**

#### 真正值钱的是它的 alpha 合成**顺序**

不是公式新颖，是顺序。把一张（可能预乘的）贴纸，合成到一张（可能半透明、可能预乘的）照片上，四步：

```
① 两边各自按需反预乘 —— 底图始终反，素材看开关
② 按模式做颜色混合        → 得到"纯混合结果"
③ 用 factor = 素材alpha × alpha 把它混回底图颜色
④ 再用 底图alpha 做第二次回混；输出 alpha 取 max(素材alpha, 底图alpha)
```

第 ④ 步是关键，两个分支各有注释：

- 底图**半透明**时：需要平稳过渡 —— **注释里带一个真实缺陷编号**，说明这是踩过坑后补的；
- 底图**全透明**时：**保持贴纸原本内容不变**，不要拿一个被 alpha 除爆的混合结果去填。

> **对我们的含义**：tespro 要解决的正是「贴纸叠照片」。**这套四步配方就是那个问题的完整答案**，
> 而且是发版代码，不是论文。

### 5.9 预乘/反预乘在美图里是一个**显式开关** `[实测·静态符号分析]`

不是隐含约定，是**接口的一部分** —— 多处独立出现 `isNeedPreMul` / `isPremultiplied` 这类开关。

三处注释给出的理由（转述）：

1. **Android 上的边缘问题** —— 不预乘，边缘会出问题；
2. **底图是棋盘格**（表示透明）时，不预乘混合会出错；
3. **贴到全透明背景上再做模糊** —— 周边采样会把透明像素当纯黑卷进来，**产生黑边**；
   对策是"先预乘做效果，输出时再反预乘回去"。

> **这条直接对应 `learn/blend/` 的缺口 2。** 玩具直接读底图 rgb 不反预乘；
> 美图不但反，还做成开关并写下三个踩坑理由。
> **第 3 条（透明背景 + 模糊 → 黑边）与我们的场景高度重合。**

### 5.11 材质·光泽层（珠光/闪片）的实装 `[实测·静态符号分析]`

§5.5 里标「只有路径名」的那一族，**这轮取到源码了**。它不是单纯叠加，是四件事叠起来（转述）：

```
① 闪片    同一张闪片图按三个不同 UV 各采一次、取最大值
          → 单一贴图做出"有厚度的闪"（三层视差）
② 亮度重映射  把唇部的平均亮度整体搬到脸部平均亮度上：
          唇修正亮度 = Lum(唇) − 平均唇亮度 + 平均脸亮度
          → 只动明度、不动色相，唇色不被环境光带偏
③ 高光抬升 亮度落在 [0.7, 0.95] 的区域向白色推 0.8
          → 只打高光，不整体提亮
④ 强度    smoothstep(0.5, 1.0, 闪片×亮度) 调制，再乘笔刷自身 alpha
```

**②「亮度重映射」是这一轮最值得抄的一条。** 它解决的是与 §5.6 色差保护同一个病：
**部件与脸的亮度基准不一致时，"贴上去"的感觉最重。**
而且它极便宜 —— 两个常数 + 一次加减。

### 5.12 柔光：美图自己的实装，一个复制了 8 次的缺陷，和一个"意图兜底" `[实测·静态符号分析]`

画笔那条路（`penTexture` / `backTexture`，共 8 段，互为副本）里有全语料唯一一处
**手写的 Photoshop 可分离混合模式**。两件事值得记。

#### (a) 一个真实的缺陷：蓝通道的门控写错，8/8 全部复制

软光的两分支写法是逐通道、逐分支手写的，于是有了这个：

```
if (S.r >= 0.5) { T.r = … }      ← 对
if (S.g >= 0.5) { T.g = … }      ← 对
if (S.r >= 0.5) { T.b = … }      ← 错：第三个又是 S.r，应为 S.b
```

`[实测]` **全语料 8 段含此公式的副本，8 段都错，0 段正确。** 是复制粘贴，从未被修。

`[实测]` 量化影响（随机彩色对 20 万组，只算蓝通道）：

| 量 | 值 |
| --- | --- |
| 平均偏差 | **3.82 / 255** |
| 最大偏差 | **33.0 / 255** |
| 偏差 > 10/255 的占比 | **15.3%** |

> ⚠️ **定位要说清**：这 8 段是**画笔（魔术笔）那条路**，不是上妆那条。
> 所以它**不影响** §5.3 的 `Color` 结论，也**不影响** `learn/blend/` —— 我们玩具的
> `softLight()` 用 `step(0.5, s)` **矢量化**写的，结构上就出不了这个错。
>
> ⚠️ 这一族里另有**注释名与表达式不符**的几处（如标 `//normal` 的式子算的是乘积）。
> **只记录观察，不断言哪个是笔误** —— 档位定义可能与直觉不同。

**这条的真正价值是那条工程教训**：**逐通道手写混合模式，出错率高到连发版代码都中招。**
美图自己在 16 档那条路（§5.8）用的是**烘焙 LUT**，恰好绕开了这类错误。
→ `[工程假设]` 我们要接混合模式，优先矢量化写法或查表，不要逐通道展开。

#### (b) 一个"意图兜底"：柔光退化时，退回 `mix`

那一族里有个专门的判定函数，注释重复出现 **7 次**：

> 「**由于柔光模式部分纯色无效果，因此使用 mix**」＋「判断是否不适用于柔光」
> ＋「**黑色需要额外增强**」

`[代码事实]` 判定规则：**妆色在三个通道上全部趋近 0 或全部趋近 1**（即黑/白与 RGB 立方体的
"角点"）时，认为柔光不适用。命中就**整个跳过混合模式**，改成直接 `mix(底图, 妆色, k)`。

```
//     blendColor1 = mix(vec4(blendColor1.rgb,1.0),color,0.8);
```

**这是全语料里唯一一条"承认看不懂"的注释**，且它指向的正是"纯黑要更弱"这条规则。
`[推测]` 结合 5 段用 0.8、2 段用"0.9 但纯黑 0.8"、1 段把纯黑分支删掉 ——
**同一个团队、同一个函数，对"极端色该给多大强度"没有共识。**
这条比任何一个具体常数都更有信息量：**它说明这不是推导出来的值，是调出来的。**

**这不是数学问题，是意图问题。** 用户选了纯黑，期望的是"涂黑"，而柔光给的是
`D²` —— 一个仍带底图纹理的深色。**模式做得对，但不是用户要的。**
美图的处理是给极端输入开一条"表达用户意图"的旁路。

> **对我们的含义**：`[推测]` 这与 D1 玩具的四格对比是同一类现象的镜像 ——
> 玩具那边是"`over` 在浓妆上盖死皮肤"，美图这边是"柔光在极端色上不表达意图"。
> **两者都说明：单一混合模式不可能覆盖全部输入，需要按输入切换或加旁路。**
> 这条对是否要在引擎里只接一个模式，是个反面证据。**注释只写了现象，理由是我的推测。**

### 5.13 掩膜怎么修：三条可搬的手法 `[实测·静态符号分析]`

§5.7 说「工程量在抠准」。既然抠出来的是掩膜，那**掩膜到手之后怎么修**才是重头。
全语料里找到三条干净、通用、可直接搬的：

#### (a) 掩膜羽化 = 掩膜自己再模糊一次，且带 `hardness` 旋钮

`[代码事实]` 有一对孪生着色器（一段沿 x、一段沿 y），就干这一件事：

```
offset = (1.0 − hardness) × 0.025 × min(1.0, scale)     ← 羽化宽度由 hardness 控
沿一个轴取 5 个点：中心、±1×offset、±2×offset
权重（x 版）  0.2254  0.2117  0.2117  0.1755  0.1755     五者相加 = 1.0
输出          RGB = 加权和；  alpha = 加权和的 R 通道
```

三个可搬的点：

1. **`hardness` 是显式旋钮**：`hardness = 1` → `offset = 0` → 完全不羽化。
   羽化宽度与"硬度"直接挂钩，**不用改贴图**。
2. **x / y 两段用的是两套不同权重**（y 版中心权重 0.3036，比 x 版的 0.2254 更尖）
   —— 合起来是**各向异性**的羽化。`[推测]` 可能是为了贴合不同形状的长宽比，
   **注释没写理由**。
3. **输出把 R 通道复制进 alpha**（源码注释：「alpha 直接使用 red 混合结果」）。
   即**约定掩膜的形状存在 RGB 里，alpha 是它的副本**。

> **对我们的含义**：tespro 的眉素材是**形状在 alpha、RGB 全白**（见 `learn/blend/README.md`），
> 方向正好相反。**搬这条必须连通道约定一起翻**，否则整块变实色
> —— 这正是 README 里坑 1 记的那类静默错误。

#### (b) 皮肤质感增强：**只加暗部细节，不加高光**

`[代码事实]` 一段带 mask 门控的清晰度着色器，三步：

```
① 9×9 均值 → 当作"低频"
② 反锐化：clamp(低频 + (原色 − 低频) × 1.8)  然后取 max(原色, 结果)
   → 与"原色"取 max 意味着**这个反锐化只会提亮、不会压暗**
③ 再叠一层：min(原色 − 模糊色, 0.0) + 0.015，乘 0.4 加回去
   → **min(…, 0) 只保留"比低频暗"的那部分**，即毛孔与阴影，**丢掉亮的那部分**
```

第 ③ 步是关键设计：**只增强暗部高频**。亮部高频是什么？是油光、反光、噪点。
**增强毛孔却不动油光** —— 这个取舍很干净，一行 `min()` 就做到了。

#### (c) 方向性模糊：顺着纹理方向糊，不横穿

`[代码事实]` 一段头发用的模糊：

```
① 从一张"梯度图"取梯度，atan2 得到方向角
② 沿该方向取 ±1…±10 共 10 个偏移点，权重来自一个 kernel 数组
③ 输出 = mix(原色, 方向模糊结果, 发丝掩膜 × gain)
```

**模糊是沿梯度方向做的，不是各向同性** —— 所以糊掉的是"杂乱"，保住的是"走向"。
`[推测]` 用于头发丝；**同一个结构可以用于眉毛毛流**，但**注释只提到 hair，这是推测。**

### 5.14 按部位扫：**各部位用的合成方式不一样** `[实测·静态符号分析]`

前几节是按关键词找的，会混进磨皮/滤镜。这一节换了筛法：**按 uniform 名判定归属**
（要求同时出现「颜色类 uniform」和「部位掩膜」），命中的才是上妆着色器。

> **筛出来的第一件事就是排除**：`cheekCleanAlpha` / `contourSmoothAlpha` /
> `perioralSmoothAlpha` / `rednessRemoveAlpha` / `nevusMask` 这一大批**是磨皮/美容，
> 不是化妆**。真正的上妆着色器只有下面几个。

#### (a) 腮红：**底图 × 颜色比例**，不是叠一个颜色

`[代码事实]` 全语料里最短的上妆着色器之一，五行核心：

```
目标色 = 底图.rgb × 颜色比例        ← ratio 不是颜色，是"乘多少"
Alpha  = (掩膜.r × 颊alpha + 掩膜.b × 鼻alpha) × 皮肤掩膜
输出   = mix(底图, 目标色, Alpha)
```

三点值得记：

1. **`targetColorRatio` 命名是诚实的** —— 它真的是个**比例**。这是**乘性染色**，
   而乘性天然保留底图的明暗与纹理（`底图 × k` 单调，纹理不会被压平）。
2. **掩膜是 RGB 三通道 = 三个不同部位**：`.r` 颊（默认）、`.g` 颊（另一套）、
   `.b` 鼻。用 `isUseDefault` 切换用哪一套颊通道。**一张贴图编码多区。**
3. **门控是 `部位掩膜 × skinMask`** —— 与 §5.4 眉部那条相反，**腮红是乘皮肤掩膜的**。

#### (b) 眼影：就是 alpha-over

`[代码事实]` 一个眼部着色器的结尾：

```
掩膜.rgb = vec3(colorR, colorG, colorB)
结果 = mix(结果, 掩膜.rgb, 掩膜.a × colorA)
```

**平色 + alpha-over。** 没有混合模式，没有保亮度。
→ 我们玩具里那一格 `over` 的"死色"表现，**就是美图眼影的实际做法**。
（差别在于**掩膜质量**与**前一级的细节增强**，不在于公式。）

#### (c) 眉弓填充 / 修容：soft-light 加高光 + 保纹理磨皮

`[代码事实]` 这一族（含 `archFillersMaskTexture`）比上面两个复杂得多，四件事：

```
① 掩膜：RGB 三通道 = 三个区，各乘一个 alpha 后取 max，再乘 皮肤掩膜 × 轮廓alpha
② 磨皮：mix(原色, 高斯低频 + (原图 − 低频), 掩膜)     ← 低频换高斯、高频保留
③ 高光：用一张"0.5 为中性"的阴影/高光图，abs(值 − 0.5) 得到偏离量，
        乘上按通道 step 选出的选择器，再乘该部位的平均色
④ 施加：把上一步得到的颜色走 soft-light 的"亮部"分支加到结果上
```

**②是保纹理磨皮的标准做法**：`低频换掉、高频留着`。这和我们 §5.11 抄到的
「亮度重映射」是**两种不同的"让部件融入"的手段**——一个动明度基准，一个动频率。

**④用的 soft-light 是矢量化写的**，所以**没有** §5.12a 那个蓝通道缺陷。同一份代码库里，
写法不同，正确性不同 —— 又一次印证 §5.12 的教训。

#### (d) 眉左右：**一份掩膜 + 左右两套参数 + 按 x 插值**

`[代码事实]` 上面那个着色器里，左右是这样处理的：

```
mixAlpha      = smoothstep(中点x0, 中点x1, 该像素的x)
平均色        = mix(左平均色, 右平均色, mixAlpha)
高光强度       = mix(左强度,   右强度,   mixAlpha)
```

**一份掩膜，左右各一套颜色/强度，交界处用一个 `smoothstep` 做横向过渡带。**

> ⚠️ **别和 §4 打架，两者是不同层面**：§4 说的是**素材导出规范**里眉是独立品类、
> 左右分开导出（一手官方文档）；这里说的是**修容这条路的着色器**怎么处理左右。
> 一个是"素材怎么给"，一个是"给了之后怎么混"。**同时成立，不矛盾。**

#### (e) 顺带：第二类"平均色"参数成了体系

`[实测]` 这一族里反复出现"某区域的平均色/平均亮度"作为 uniform：
`fAverageColor`、`fLeftAverageColor` / `fRightAverageColor`、`fAverageRed`、
`averageFaceLuminance`、`averageLipsLuminance` …

**这些值都由 CPU 侧算好传进来**（着色器里算不出全图平均）。含义：
**美图把"局部相对全脸的统计基准"当成一等公民**，而不是让着色器自己去猜。
这与 §5.11 的亮度重映射、§5.6 的色差保护，是同一个思路的三次出现：
**先建立基准，再谈叠色。**

`[代码事实]` **§5.14(c) 没说完的那一步，在修容那条路里闭合了** —— 平均色不是拿来做
肤色归一，是拿来**当高光的颜色**：

```
阴影/高光图取值 s（0.5 为中性）
强度 = (s − 0.5) × 该通道的 lightAlpha
高光色 = 强度 × fAverageColor + vec3(0.5)      ← 染的是"这个部位自己的平均色"
结果   = softLight(原色, 高光色)
```

**高光不是白色，是"这个部位本来的颜色被提亮"。** 这一条比公式本身重要：
它解释了为什么成套的修容能融进皮肤 —— **它提亮的颜色采样自皮肤自己。**

### 5.15 唇 / 修容 / 材质 / 调色：四条还没写到的路

#### (a) 唇：有一条路根本不是"上色"，是"去唇纹" `[代码事实]`

> ⚠️ 先澄清，免得和 §5.3、§5.5 打架：**唇的着色**走 W3C `Color`（§5.3）。
> 这一段是**另一条路** —— 唇纹/唇印去除，两者在同一个库里并存。

一段 5 行的唇部着色器，核心就两行：

```
目标色 = mix(底图 + 残差 − 0.4, 残差, step(0.5, 用云端结果))
输出   = mix(底图, 目标色, 去纹强度 × 唇掩膜alpha)
```

三个值得记的点：

1. **两个数据源二选一**：`useCloudResult` 为假时走**本地残差回注**（`底图 + 残差 − 0.4`，
   加法式），为真时直接用**云端算好的结果图**。**同一个着色器，端侧与云端两条路。**
2. **本地那条路不用掩膜**：`唇掩膜alpha = mix(1.0, 掩膜.r, step(0.5, useCloudResult))`
   —— `useCloudResult=0` 时掩膜恒为 **1.0**，也就是说**本地路径是整图生效的**。
   `[推测]` 这说明本地残差本身已经是"只在唇上非零"的图，不必再乘掩膜；
   **但也不能排除是省一次采样** —— 静态读不出意图，只记录事实。
3. **`− 0.4` 是偏置项** `[推测]`：若残差图以 0.4 为均值编码，这一项就是去直流。
   **不猜死** —— 要确认得知道那张图的写入端，不在这个库里。

#### (b) 修容 / 填充：掩膜的 alpha 通道不是覆盖度，是**元数据** `[代码事实]`

`[0277]` 与 `[0345]` 里最反直觉的一条：

```
faceidAlpha = step(掩膜.a, 上限) × step(下限, 掩膜.a)
```

**用双阈值把 alpha 卡成一个区间**，且原注释写着 `//效果分人脸`。
→ **`.a` 通道承载的是"这张脸是谁 / 属于哪一档"，不是"这里要不要上妆"。**
掩膜的 RGB 才是形状（三通道 = 三个区，同 §5.14）。

对我们是硬提醒：**移植这类掩膜时，不能假定"多出来的通道是备用"**。
`[工程假设]` 我们的素材里若也出现"多通道但只用了一个"，先假设**其余通道有语义**。

同族还有两条：

- **`sampling25D`**：`mix(标准UV, 2.5D展开UV, 参数)` —— **两套 UV 之间插值**，
  用来在"平面贴图"和"2.5D 展开贴图"之间做过渡。`FortunaBrowArchFillers25D`
  这个资产名与它对应（§5.10）。
- **两个滤波器拼出纹理**：`高频 = 原图 − 中值`，`结果 = 高斯 + 高频`。
  与 §5.13 / §5.14(c) 的"低频 + 高频"是**同一个骨架，换滤波器**：
  那两处是「高斯低频 + 原图减高斯的残差」，这里是「**高斯低频 + 原图减中值的残差**」。
  **中值对椒盐/毛孔这类孤立点不敏感** → `[工程假设]` 用于保毛孔比保走向更合适。

#### (c) 材质 / 程序化纹理：三个倍频挤进一张图 `[代码事实]`

一段材质叠加着色器，四件事都能搬：

```
① 同一张材质图，三个缩放取三个通道：
     全尺寸取 .r    ×0.5 取 .g    ×0.25 取 .b
② 按 faceRatio.x 的 256/512 两档阈值选用哪个倍频（分辨率自适应）
③ 左右镜像：if (symTexture>0.5 && x>0.5) x = 1.0 - x
④ 用软光做 USM 锐化：先反解出"要达到当前亮度差所需的 blend 参数"，再喂给软光
```

**①是多倍频噪声的贴图化**：三张不同尺度的噪声放进一张纹理的三通道，**一次采样拿三档**。
**②是关键**：阈值挂在 `faceRatio`（一个 vec2）上 —— **输入图多大，就换用哪个倍频**，
这样同一个材质在 500px 和 2000px 的输入上**视觉尺度一致**。`[工程假设]` 对照我们的处境：
照片尺寸不固定，任何"按像素写死"的纹理尺度都会在大图上变成噪点、小图上变成色块。

**③是眉左右问题的第二种解法。** §5.14(d) 是「一份掩膜 + 左右两套参数 + 按 x 插值」；
这里是「**把右半边镜像映射回左半边**，共用同一份采样」。
两者都能保证对称，但**后果不同**：插值法允许左右真的不一样（可以左浓右淡），
镜像法**强制左右完全相同**。选哪个取决于要的效果，不是哪个更先进。

**④是一条可复用的桥**：`BlendSoftLightf` 的输入不是"一个 blend 色"，而是
"**为了让输出接近某个目标，blend 参数应该是多少**" —— 它把软光当**可逆变换**用。
`[理论]` 用软光实现 USM，比线性 USM 更不容易在高光/阴影处溢出。

`[实测]` 它的门控叠了**四重**：`强度 × 皮肤掩膜 × (1 − 面部皮肤掩膜) × 全脸轮廓`。
最后那个 `(1 − smoothstep(0,0.25, mask))` 是"**先软化再反相**"，与 §5.6 的
`maskAlpha = smoothstep(0.05,0.95,mask)` 是同一手法换了参数。

#### (d) 调色：3D LUT 是**级联**的，而且方向靠正负号 `[代码事实]`

`[实测]` 全语料 **16 段**用同一个 `lut3d()` 辅助函数：标准 **16³ LUT 打包进 2D 纹理**
（64px 一格、`fract(blueColor)` 在两张切片间插值）。用法上有两条值得记：

1. **串联，不是并联**：
   `第一步 = mix(原图, lut3d(原图, 肤色LUT), 强度)`
   `第二步 = mix(第一步, lut3d(第一步, 暖/冷LUT), 强度)`
   **第二级吃第一级的输出。** 所以"肤色校正"和"冷暖"不是两个独立叠加的层，
   而是**有先后的一条链**。顺序换了结果会不一样 —— 这是可实测的 `[理论]`。
2. **一个有符号标量同时编码方向与强度**：`alpha > 0` 走暖、`alpha < 0` 走冷，
   强度都是 `abs(alpha)`。**接口上一个 float 顶两个参数**，比 `(方向, 强度)` 少一个 uniform。
3. **集合差分离五官**：`五官掩膜 = clamp(面部解析 − 皮肤掩膜, 0, 1)`，
   直接拿两个掩膜相减。而且**皮肤用满强度、五官只给 0.7** ——
   **"五官要轻一点"是被写死在代码里的**，不是靠参数调出来的。

#### (e) 公共头被逐字节复制，里面的函数有**从来没被调用**的 `[实测]`

`RGBtoHCV` / `RGBToHSL` / `HUEtoRGB` / `HSLToRGB` / `BlendSoftLightf` / `blendSoftLight`
这一整块在多个文件里**逐字节相同** —— 是**内联复制**，不是 `#include`。

复制带出来的三个可测事实：

| 事实 | 数字 |
| --- | --- |
| `BlendSoftLightf`（带 `rate` + `clamp(base−0.35)` 偏置的自定义版）定义 | **3 段** |
| 其中**真的调用**它的 | **1 段**（另 2 段是**死代码**） |
| `blendSoftLight`（标准版）定义 / 调用点 | 12 段 / **48 处** |

**→ 主流是标准矢量化那条，自定义那条是少数派里的少数派。**
（这和 §5.14(c) 的印象相反 —— 是查过全语料才改过来的。）

写法分布：**手写 `if (blend > 0.5)` 分支 3 段，矢量化 `mix(…, step(0.5, blend))` 11 段。**
`[工程假设]` 矢量化占多数**可能**正是 §5.12a 那类逐通道手写缺陷没扩散开的原因。
`[推测]` 也可能只是新代码用了新写法、老代码没重写 —— **静态区分不了，只记录分布。**

#### (f) "绝不满量"是一个**家族**，不是一个常数 `[实测]`

全语料里作为天花板出现的 `<1` 乘数：**0.8 / 0.9 / 0.92 / 0.95 / 0.97 / 0.975**。
出现在 `maskAlpha`、`mouthColor`、`stroke_center`、`overlapBlendFactor`、`levelRedGreen`、
`hueParam.y` 等各式变量上。

**同一个意图（"别做到底"）在不同代码路径取不同值** —— 与 §5.6 的 `0.975`、
§5.12b 那三档兜底常数（0.8 / 0.9 / 0.9+0.8）是同一个设计习惯。
`[工程假设]` 这不是某个公式的系数，是**团队共识式的留白**。
→ **我们接的时候也应该带一个显式的 `ceiling` 参数**，而不是让它等于 1。

#### (g) `uniform` 被当成编译期开关用，至少 8 处 `[实测]`

| 开关 | 作用 |
| --- | --- |
| `isUseDefault` | 腮红用哪一套颊通道（§5.14a） |
| `useCloudResult` | 唇：本地残差 vs 云端结果（本节 a） |
| `isMouth` | 同一段代码切成眼妆 / 唇妆两用（§5.4） |
| `symTexture` | 材质左右镜像开/关（本节 c） |
| `adjustHighlight` | 软光锐化那段整个跳过（本节 c） |
| `miniFaceOpt` | 小脸模式换门控公式（§5.14b 的 `mix(skinColor, contourMask, ·)`） |
| `multiScaleMaterial` | 材质多倍频开/关（本节 c） |
| `sampling25D` | 平铺 UV vs 2.5D UV（本节 b） |

**同一份 GLSL，用 uniform 做变体，而不是编译多份。**
`[理论]` 代价是**两个分支都会被求值**（GPU 上 `if` 不省算力），
所以这些分支里的工作量都刻意压得很小（一个 `mix`、一次采样）。
`[工程假设]` 对我们是可抄的：**少一份着色器就少一次编译和一次状态切换**，
静态照片路线下这点开销无所谓，换来的是**着色器数量可控**。
（**注**：本节只列了 8 处，实际远不止 —— 光是 §5.16(a) 那个分派器家族自己就另有 8 个开关。）

### 5.16 混合分派器 / 闪粉 / "亮度"到底是什么 `[实测·静态符号分析]`

#### (a) 分派器家族：**混合的两个操作数，谁上谁下是运行时开关** `[代码事实]`

`[实测]` `isNeedColorWithMaterial` 落在**和 §5.12a 那个蓝通道缺陷完全相同的 8 段**上
（`0084 0281 0282 0291 0311 0350 0477 0516`）。这一族是个**混合模式分派器**：

```
vec4 blendColor(int blendMode, vec4 S, vec4 D)   // blendMode 是运行时 int
```

四件对我们直接有用的事：

1. **`swapBlendLayers`：交换 S 和 D。**
   `blendColor(6, 妆色, 材质)` 与 `blendColor(6, 材质, 妆色)` 是**两个不同结果** ——
   PS 系混合模式**不可交换**。同一段里还有第二个顺序开关 `swapOrder`
   （交换两个图层），**一段代码里两处独立的"谁是底"**。
   → **这正是我们 D1 缺的第二块**：我们不但只有一个模式，还把底图/妆色的角色写死了。
2. **`blendColor` 返回 `vec4(T, S.a)`** —— **模式只改颜色，alpha 一律取上层**。
   即"混合模式的输出不带自己的覆盖度"，覆盖度是另一件事。（同 §5.8 的四步法。）
3. **`blend()` = Porter-Duff over + 反预乘**（`rgb = rgb/alpha`），带两个 early-out
   （`dstColor.a<=0` 直接返回上层）。**与 §5.9 的配方同形**，这是它在语料里的又一次出现。
4. **`isNeedColorWithMaterial` 的语义**：为真 → 用 soft-light（mode 6）把妆色**烧进材质层**；
   为假 → 由 `needColor` 决定要不要直接替换 rgb。**即"材质层要不要跟着颜色走"。**

> `[代码事实]` **一处命名与实现不符，和 §5.8 是同类现象的第二次出现**：
> `blendMode == 2` 的公式是 `D*S`（= multiply，**没有注释**），
> 而 `blendMode == 3` 顶着注释 `//multiply`，公式却是 `(1-D)(1-S)`（= **screen**）。
> **要么注释错位一行，要么实现标错 —— 静态分不出是哪个**，只记录。
> §5.8 那次是 16 档 LUT 里 13/14 的注释名互换。**两次都在"模式编号 ↔ 名字"这层**，
> `[推测]` 说明编号与名字是两处独立维护的。

#### (b) 闪粉 / 珠光：三条可直接搬的手法 `[代码事实]`

一段闪粉着色器，比 §5.11 记的那版更完整：

1. **三个尺度视差，压力分层出现**：
   三套 UV（`vGlitterPatternTexcoord1/2/3`）采**同一张**图案图，取 `max` 合成 →
   **一次贴图拿到三层视差**。第 2、3 层额外乘 `smoothstep(0.3,1.0,笔刷alpha)` /
   `smoothstep(0.7,1.0,笔刷alpha)` → **笔刷越重，出现的层越多。**
2. **不透明度反过来当对比度**：`power = 1.0 + 5.0*(1.0 − 笔刷alpha)`，
   掩膜先 `pow(mask, power)` 再用。
   **笔刷越轻，指数越大 → 掩膜越稀疏 → 只剩峰值亮点。**
   这就是"轻扫时是零星闪、重涂时是成片亮"的实装 —— **不是换贴图，是一个 `pow` 的指数。**
3. **亮度重映射，逐字对上 §5.11**：
   `唇部修正亮度 = Lum(原色) − 平均唇亮度 + 平均脸亮度`，
   再用 `mix(·, 唇掩膜)` 只对唇生效；随后
   `亮度因子 = 修正后亮度 ÷ 平均脸亮度`，**闪粉亮度随皮肤明暗缩放**；
   峰值处 `mix(笔刷色×亮度因子, vec3(高光值), smoothstep(0.5,1.0, 掩膜×亮度因子))`
   —— **推向一个显式的高光值**（§5.11 的高光抬升）。
   防零用 `平均脸亮度 + 0.5×step(平均脸亮度, 0.0)`。

> **结论确认**：§5.11 记的两件事（**亮度重映射** 与 **高光抬升**）在这条路上**同时出现且逐字吻合**。
> 这两条不是我从一处孤例推的，是**至少两条独立代码路径共有的**。

#### (c) "亮度"在这个代码库里**不是一个东西** `[实测]`

| 口径 | 系数 / 形式 | 段数 |
| --- | --- | --- |
| **Rec.601 亮度** | `0.299, 0.587, 0.114` | **26** |
| **W3C `Color` 那条路** | `0.3, 0.59, 0.11` | 7 |
| **YIQ**（带色度矩阵） | 同上 Y + `0.956/−0.272/−1.106…` | 4 |
| **HSL / HSV** | 整数 hue、`RGBToHSL` 等 | 15 |

**主流是 Rec.601（26 段），W3C 那组只出现在 `Color` 混合这一条路上。**

`[理论]` 两组系数数值很近（0.299 vs 0.3），但**不能混用**：
要跟 W3C 规范 / 跟 PS 对照，`Color` 模式就必须用 W3C 那组。
`[工程假设]` **移植时把亮度口径设成一个显式常量**（我们在玩具里已经有 `lum()`），
别在每一处各写一遍数字 —— 这个库里四个口径并存，本身就说明了散写的代价。

`[代码事实]` YIQ 那条路只干一件事：**把颜色转到 YIQ，只动 Y，再转回来**。
`细节 = Lum(输入) − Lum(平滑)` 加到笔刷色的 Y 上、`clamp` 回 [0,1]，
**色度完全不动** —— 这是"只换明度细节、不碰色相"的最干净实现。
另有一路把两个增益都挂在 **0.7** 这个阈值上（亮部加、暗部压、`smoothstep(0.7,0.95,Y)` 推高光）。

#### (d) 用"重复同一行"做效果加强 —— 确认 **2 处**，不是 7 处 `[实测]`

| 文件 | 连写次数 | 那一行 |
| --- | --- | --- |
| `0098` | **5** | `mix(outputColor, glitterColor, 掩膜×…)` |

—— **一个不用改参数的"把效果做重一点"旋钮。**

#### (e) 软光至少有**四个**变体 `[实测]`

| 变体 | 定义段数 | 特点 |

## 6. 学术界：妆容迁移系统性回避眉毛

- **BeautyGAN（ACM MM 2018）`[一手·读原件]`**：makeup loss 只作用于
  "lips, eye shadows and face regions" **三区**，眉毛不在其中；
  构造眼影 mask 的原文明确写 *"exclude eyes regions, some hair and **eyebrow regions** in between"*。
- **PSGAN / PSGAN++ / CPM / SSAT**：全文检索 **`eyebrow` 出现 0 次**。`[一手·读原件]`
- 唯一正面处理原生眉毛的是 **Tong et al., Example-Based Cosmetic Transfer（Pacific Graphics 2007）**
  `[二手]`，流程是：

  ```
  Bayesian matting 抠掉眉毛/睫毛  →  inpainting 补皮肤  →  妆映射  →  用 alpha 把眉毛合成回去
  ```

  注意顺序：**先把眉毛从皮肤上移除，再合成**；不是在眉毛上堆高 alpha。

> 即：**深度学习时代的妆容迁移文献里，没有一篇正面解决"如何盖住原生眉毛"。**
> 现成参考只有 2007 年那条 matting + inpainting 老路。

## 7. 对本项目的含义

1. **架构不必自我怀疑。** `关键点 + UV 贴图` 就是美图主力产品线的做法。§0.2 的问题
   不是"选错了技术路线"，是"参数口径借错了品类"。

2. **§9.0 的指标值得重估。** 现在把"真眉透过率 ↓ 接近 0"当硬指标、路径是提 `peak`。
   但美图（`eyebrow_deepen`）与 2007 年那条老路都指向：在**浓密原生眉**上，
   "靠 alpha 盖住"是被动打法。**要不要换思路，需要拍板，本文不代决。**

3. **§0.2 的根因只对一类用户成立。** 生成器里 `fill-*` 三档的注释写的是
   "给稀疏 / 脱落眉毛用（**化疗后、天生稀疏**）"。这类用户原生眉本就不存在或很稀，
   **没有"盖不住"的问题**；"盖不住"只咬**原生眉浓密、但想换眉形**的用户。
   两类人的诉求相反——是否为后者改架构，是产品决策。

4. **美图 API 用不了**（需企业认证，见 `ai-engine-api-spike.md` §1.1），
   但其**素材规范是一份免费的对照口径**：眉毛独立品类 + 左右分开导出。

5. **"从图里抠眉"这条路，素材是够的，但只够做"增强"，不够做"换眉形"。** `[实测]`
   在 `tespro/learn/blend/face-local.webp`（303×303）上按通道扫：

   | 量 | 值 |
   | --- | --- |
   | 左眉 bbox | u∈[0.300,0.460] v∈[0.563,0.597] → **48×10 px** |
   | 眉 / 皮肤 亮度分离 | **≈44**（灰阶单位，阈值 110） |
   | 同法量错位置时（量到头发） | 分离 **191** |

   两条含义：
   - **可分离，但不干净**：44 是"软过渡"，不是二值边界。做局部加深/提对比够用；
     要拿它**驱动形状**（把原生眉变成另一个眉形），分辨率与信噪比都不够。
   - **分离度对窗口位置极度敏感**（44 vs 191）。任何"眉毛可提取性"的结论
     都必须连**测量窗口**一起报，否则数字无意义。

   而且**受众是反的**：这条路服务的是**原生眉浓密**的人；生成器 `fill-*` 三档
   写的目标用户（化疗后 / 天生稀疏）**根本没有眉可抠**。见 §7 第 3 项。

6. **D1「叠加模式」这条，选型已经被验证，只剩把它接进引擎 —— 但缺口是两块。** `[代码事实]`
   `learn/blend/` 那个 `color` 模式 = 美图发版用的 `Color(Cb,Cs) = SetLum(Cs, Lum(Cb))`，
   逐项同形（§5.3）。且美图在相同取舍上留下了产品口径注释，理由与我们一致。
   **不需要再论证"该不该用 `Color`"，要做的是两件小事**：
   补上 `ClipColor`（玩具现在缺，会换色相），以及确认底图是非预乘。
   接进引擎的前提仍是**让底图成为 shader 可读的纹理**（见 `learn/blend/README.md`）。

   **✅ 2026-09-14 深夜：三件事都在玩具里做完了**（`tespro/learn/blend/`，**没碰引擎**）：
   ① 补上 `clipColor()`，并留 `?clip=0` 开关；② `lum()` 的口径从 Rec.601 改成
   **W3C 的 `0.3/0.59/0.11`**（原先一边声称"逐项同形"一边用了另一组系数，见 §5.16c）；
   ③ 把"谁是底/谁是顶"从写死改成 `uSwapLayers` 开关。
   `[实测]` 三项都在浏览器里核过（截图逐像素比对）：
   ClipColor 只影响 `color` 一格（其余三格差异像素恒为 0），**>2/255 的像素仅 1.09%、
   最大 49/255、均值 0.07** —— 印证了"四格对比图看不出这件事"。
   验伪点：`?asset=11&alpha=1&swap=1` 时 **multiply 逐像素恒等（0 个不同）**，
   而 over 89 / soft-light 41 / color 94。

   **⚠️ 但 §5.16(a) 查出来还有第二块缺口：谁是底、谁是顶，也是一个开关。**
   `[代码事实]` 美图的分派器里同时有 `swapBlendLayers` 与 `swapOrder` 两个独立开关，
   `blendColor(6, 妆色, 材质)` 和 `blendColor(6, 材质, 妆色)` 是**两个不同结果**
   —— PS 系混合模式不可交换。**我们的玩具把底图固定在 `base`、妆色固定在 `src`，
   角色是写死的。** 接引擎时要连同这一点一起改，否则等于只搬了一半。
   同族还有一条：`blendColor` 返回 `vec4(模式结果, S.a)` —— **模式只改颜色，
   覆盖度一律取上层**，两件事不要混在一个返回值里。
   （**注**：实测中发现 **"可交换"要说清楚是核可交换还是合成可交换** ——
   multiply 的核 `D*S` 可交换，但 `mix(底层, 核, a)` 不可交换，
   所以 a<1 时它照样变。只写"multiply 可交换"是会误导的。）

7. **1193 段全扫完之后的总结论：这类引擎的工程量在「抠准」和「贴对」，不在「调色」。**
   `[实测]` 语料归类里分割/掩膜是最大一块（§5.7），而 91 条「为什么」注释里反复出现的是
   **黑边、羽化丢失、边缘过渡、预乘** —— 不是配色。这与 §5.4「门槛在分割，不在运算」
   互相印证。**对我们的含义：继续在公式上找突破是低效的**；该投入的是
   「底图可读 + 区域抠准 + 边缘正确」。三处直接可抄的手法已记在
   §5.8（四步合成顺序）/ §5.9（预乘开关的三个理由）/ §5.11（亮度重映射）。

8. **接混合模式时，不要逐通道手写。** `[实测]` 美图发版代码里 8 份手写软光，
   **8 份全部有同一个蓝通道门控错误**（§5.12a）；而它 16 档那条路用**烘焙 LUT**，
   恰好绕开了这类错误。→ 我们接的时候优先**矢量化写法或查表**。
   另：§5.12b 表明**单一混合模式覆盖不了全部输入**（柔光在极端色上不表达用户意图，
   美图的办法是开旁路退回 `mix`）—— 这是"引擎里只接一个模式"的反面证据。

9. **"上色 = `Color`"要收回，改成"按部位分"**（§5.14，2026-09-14 深夜修正）。
   `[实测]` 按 uniform 名（而非关键词）筛出真正的上妆着色器后：
   **腮红 = 乘性染色**、**眼影 = 纯 alpha-over 平色**、**眉/眼/唇加深 = 纯减法压暗**、
   **眉弓填充/修容 = soft-light 加高光**。`Color` 只对**唇的材质那条路**成立。
   → **含义：不要指望一个混合模式解决所有品类。** 我们玩具四格对比里
   `over` 的"死色"表现，**恰好就是美图眼影的做法** —— 差别在**掩膜质量**与
   **前一级的细节增强**，不在公式。**这再次指向 §7 第 7 项：投入该在抠准，不在调色。**

10. **两条能直接改我们做法的细节**（§5.14e / §5.15b）：
    - **要"提亮/加深"任何一个部位，颜色都应从该部位的原图统计里取，不该用预制色。**
      `[代码事实]` 美图的高光色 = `强度 × 该部位平均色`（该平均色由 CPU 侧算好传入）。
      **高光不是白色。** 静态照片路线下算局部均值几乎免费。
    - **别假定掩膜多余的通道是备用。** `[代码事实]` 修容掩膜的 `.a` 被
      `step(·,上限)×step(下限,·)` 当作**"属于哪一档 / 是哪张脸"的元数据**用
      （原注释 `//效果分人脸`），不是覆盖度；腮红、`wakeMask` 也各自用多通道编码多部位。
      **移植素材时先假设其余通道有语义。**

11. **「怎么做到和它一样的效果」—— 拆成五层，按每单位工作量的观感收益排**（2026-09-14）。
    `[代码事实]` 为此把 tespro 9 对 shader 全读了一遍。结论是：**比预想的更近，也更远。**

    | 层 | 现状（`[代码事实]`） | 缺什么 | 成本 |
    | --- | --- | --- | --- |
    | **0 · 妆层读到底图** | 9 个 fragment shader **没有一个采样照片**，全是 `fragColor = vec4(某颜色, alpha)`，靠 three 的 `transparent:true` 默认 alpha-over | 一个 `WebGLRenderTarget`：先渲 `videoPlane + faceVideoMesh`，再把这张 target 当 `uBase` 传妆层 | **小**（管线已备好，见下） |
    | **1 · 换对模式** | 只有 over（§5.5） | 按部位分派（§5.14） | **小**，且与层 0 同一处代码 |
    | **2 · 抠准边界** | `_FaceMaskE` = `foundation_mask.PNG`，**静态贴图**，不是运行时分割 | 最小项：给 mask 加 `hardness` 做 `smoothstep` 羽化（Meitu 有显式旋钮，§5.13）。完整 face parsing 是另一个量级 | 羽化 **中** / 分割 **大** |
    | **3 · 贴对配准** | 脸网格 + landmark 有，`_Brow_ST` 有 | 驱动参数从 landmark 算出来（现在是静态 ST） | **大** |
    | **4 · 参数系统** | 一部位一张贴图 | 一部位 = 一张 mask + 一组参数 | **大**（长期） |
    | **5 · 素材** | `[实测]` 眉峰值 alpha 只到 0.639 / 0.498 / 0.408，眼影能到 0.95+ | 把眉的峰值拉到能盖住 | **中**，纯素材，可并行 |

    **层 0 比想象中近** —— 管线里三块拼图已经在了：
    - 妆层网格**共用脸部几何**（`MakeupEngine.js:336` `new Mesh(mesh.geometry, this.blushMat)`），
      妆层和脸在同一坐标系；
    - `assets/shaders/facewarp/vertex.glsl` 已经把屏幕空间 UV 算好了
      （`vec2 ndc = baseClip.xy / baseClip.w; vUv = ndc * 0.5 + 0.5;`）；
    - 渲染顺序被注释写死：`renderOrder = 1; // above the background plane + blur, below makeup colors`；
    - 唇 shader 里甚至已经有 `in vec4 vClipPos`。

    **两个必须一起处理的副作用 `[代码事实]`：**
    - **魔法折半常数是 over-only 的补丁。** `blush` 里 `alpha*0.7`、`lip` 里 `alpha*0.4`、
      `foundation` 里 `*_shedat*0.5` —— 接了底图之后必须重新推，否则双重变弱。
    - **腮红是占位符。** `loadBlushMat` 传的是 `_EyeShadowTexture: blushTexture` +
      `_FaceMaskE: foundation_mask.PNG` —— **uniform 名全是眼影的**，shader 是眼影那份的
      拷贝（连 fresnel 与 `alpha*0.7` 一起抄的），颜色硬编码 `_ShadowColor: (1, 0.3, 0.4, 1)`。
      **它不是"效果不够好"，是还没真正写过。**

    **`[推测]` 一个要先拍板的岔路口：** Meitu 的 `rgbImage` 是**累积图**（每段吃上一段的
    输出），所以它能做频率分离、多级 LUT 级联。而 tespro 现在是**各部位独立 mesh 靠
    alpha-over 叠**。做层 0 时会碰到同一个选择：`uBase` 是"只有照片"，还是"照片 +
    已上过的妆"？可证实的方法是找美图有没有 ping-pong 的 render target 分配逻辑 —— **未做。**

    ⚠️ **层 0 会碰 `src/core/`，与「只在 learn 里面做」冲突。** 要么松约束，要么先在
    `learn/` 里做 render-target 最小原型（不改引擎，只证明这条路在 tespro 的管线里通）。

    > **一句实话**：逐像素一致做不到，也不该做 —— 我们没有它的分割模型、landmark 精度、
    > 素材库和云端。目标是**同一档次的观感**。而且层 1（调色）单独做提升有限
    > （§7 第 7 项、§5.16）。排序是 **层 0 → 层 1 → 层 2 羽化 → 素材**。
